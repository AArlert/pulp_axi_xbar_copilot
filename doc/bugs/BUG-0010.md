# BUG-0010 — `MaxMstTrans` 在飞上限粒度：spec 扁平口径 vs demux 文档分桶机制

> 状态：OPEN（SPEC_ISSUE，待 rev 仲裁）。本页为 in-progress 详情页——
> `fix`/`rerun`/`regression_guard` 三段在仲裁前如实留白/记待办，非编造。
> 本页只陈述症状/事实与两种读法各自的依据，**不预判裁决结果**（裁决权属 rev）。

## symptom

`MaxMstTrans`（基线 =10）的"每 slave 端口在飞事务上限"粒度在许可来源间不一致：

- **读法 A（扁平）**：spec.md §5.4.1「每 slave 端口 in-flight 事务数 ≤ `MaxMstTrans`」
  与 §2.1 字段表「每个 slave 端口最多同时 in-flight 的事务数上限」——读作**每 slave
  端口一个扁平计数上限**。
- **读法 B（分桶）**：`vendor/axi/doc/axi_demux.md` §Ordering and Stalls→Implementation
  描述实现为「每个（低位 ID 桶 × 方向）各一个独立计数器，每个独立封顶 `MaxTrans`」——
  据此，单 slave 端口的合计在飞数在流量摊满全部 ID 桶与两个方向时可达
  `MaxMstTrans × 2^AxiIdUsedSlvPorts × 2`（基线即 `10 × 2^3 × 2`），远大于扁平
  读法的 10。

两种读法给出的"上限被顶到"判据阈值不同，M2/M3 事务数上限 checker 的期望值粒度
取决于采信哪一种。

## first_anomaly

非仿真发现（静态比对，未跑仿真）。M2 场景规划时，为 `MaxMstTrans` 上限场景
（testplan M2-TL01）推导期望值，逐条比对两处许可来源：

- spec.md §5.4.1 + §2.1 `MaxMstTrans` 行；
- `vendor/axi/doc/axi_demux.md` §Ordering and Stalls 下的 **Implementation** 小节
  原文：「`2 * 2^AxiLookBits` counters track the number of in-flight transactions.
  ... there is one counter for write transactions and one for read transactions.
  Each counter can count up to (and including) `MaxTrans` ...」（`axi_demux` 的
  `MaxTrans`/`AxiLookBits` 即 `axi_xbar` 的 `MaxMstTrans`/`AxiIdUsedSlvPorts`）。

发现二者对同一上限给出的粒度不同——扁平 vs 分桶——即本条。

## rca

1. spec.md 蒸馏 `MaxMstTrans` 时采信了主文档 xbar.md §Configuration 表的顶层
   一行定义（+ axi_pkg.sv L489-491 注释「each master connected to the crossbar
   ... in flight」），两者都只给"每 slave 端口一个上限"的扁平表述，未提按
   （约简 ID × 方向）分桶。
2. 该扁平表述是顶层配置表对参数的**概括**；参数实际作用的计数机制描述在结构上
   属于下层部件 `axi_demux`（`axi_xbar` 每 slave 端口例化一个），其文档
   axi_demux.md 的 Implementation 小节给出了分桶（`2 * 2^AxiLookBits` 个计数器、
   读写分离、每桶独立封顶）的更精细描述。
3. spec.md 蒸馏时未把下层部件文档的这一精细机制并入 §5.4，于是同一上限在
   spec.md（扁平）与 demux.md（分桶）之间出现粒度分歧。
4. 注：spec.md §5.2 既有条款在描述"同 ID 判定只比较低 `AxiIdUsedSlvPorts` 位"时
   已引用同一 demux.md §Ordering and Stalls 段落为可信源——即该下层文档段落此前
   已被本 spec 采信过（用于 ID 比较部分），但其相邻的计数器分桶描述未被一并采信。
   本条陈述此事实，不据此推断应采信哪一读法。

## fix

**REV-005 仲裁裁决（2026-07-27）：SPEC_CHANGED —— 采分桶口径。**

rev 独立核验许可来源原文（未采信 arch 提案）：xbar.md L46（`MaxMstTrans` =
"Each slave port can have at most this many transactions in flight"，扁平）与
axi_pkg.sv L489-491（同扁平）；demux.md L70-74（§Ordering and Stalls→
Implementation）明述实际机制为 `2*2^AxiLookBits` 个（约简 ID 桶 × 方向）**独立**
计数器、各封顶 `MaxTrans`、各带一个"目标 master 端口"绑定寄存器（L74 明述该同一
计数器机制**同时**承载"换目标即 stall"（§5.2）与"计数封顶"）。基线
`AxiIdUsedSlvPorts=3<5` ⇒ 基线真有 `2^3×2=16` 个独立计数器，扁平读法在基线即被
机制违反。

**裁决**：采信 demux.md 的按（约简 ID 桶 × 方向）分桶计数模型。三条理由：
(1) **机制精确**——demux.md 描述的是实际例化子模块（每 slave 端口一个 axi_demux）；
扁平表述仅为顶层配置表的粗略概括。(2) **不假红**——采扁平口径会令 M3/M4 跨桶
场景在 DUT（真按分桶合法接受 >扁平上限）时假红。(3) **来源合法、非 spec-from-RTL**
——分桶细节全部来自上游文档 demux.md（spec 开篇已列为可信"下层部件佐证"，且 spec
§5.2 既有条款已引用同一 demux.md 段落）+ axi_pkg L510 显式"see `axi_demux` for
details"指针 + spec §1 拓扑，**不触碰 RTL 实现体**。与 BUG-0005（主文档胜）非矛盾：
同一"取机制精确且不假红者"原则在不同来源分布下的落点（BUG-0005 是 doc vs 软性
源码注释；本条是粗略概括 doc vs 机制精确 doc）。

**orch 应用范围**（rev 只出裁决，spec 正文编辑 + sha256 重 pin + 本 bug 状态转
SPEC_CHANGED 由 orch）：§2.1 `MaxMstTrans` 行 + §5.4.1 改为分桶口径（每（约简 ID×
方向）计数器独立 ≤ MaxMstTrans、各带目标端口绑定寄存器），标注该计数器机制即 §5.2
stall 的底层机制（二面一体）；依据栏记 demux.md §Ordering and Stalls→Implementation
+ axi_pkg L510 + §1/§5.2。**受影响 design-prompt 再锚定**（REV-005 条件 C1）：
`sva_bind.md` C3.4 / `scoreboard_refmodel.md` C5.3 / `functional_coverage.md`
`cg_tx_limit` 三处现直引 demux.md 的分桶依据，须改引新 spec §5.4 条款（恢复 DV
单一事实源为 spec.md）。详见 `doc/review/REV-005.md` §3。

## regression_guard

paths: doc/testplan.md, tb/sva/axi_xbar_txlimit_sva.sv
过渡性收敛（仲裁前既有，事实陈述）：testplan M2-TL01 已刻意收窄到**单一（低位
ID 桶 × 方向 × 目标 master 端口）三元组**构造——该简并情形下扁平与分桶读法给出
**同一**阈值（=`MaxMstTrans`），故 M2-TL01 checker 不依赖裁决即可落地。

**REV-005 裁决后的长期守卫方向**（rev 只给方向、不写实现）：M2-TL01 收窄三元组
**不能区分**两读法，故它**不是**本条的回归守卫。裁决落地后须由 planner 注册一条
**M3/M4 跨桶定向场景**：把 ≥2 个 ID 桶各压到接近 `MaxMstTrans`、令单 slave 端口
合计在飞数**远超扁平上限**、确认 DUT 合法接受——该场景同时把"采分桶"从 demux.md
文档信任**升级为波形经验确认**（若 DUT 反而表现为扁平，则触发对 demux.md 的
DUT_BUG/文档-实现分歧复核）。此守卫随 M3/M4 规划落地。
