# BUG-0026 — 已登记证据被静默截断：SVA 逐条命中数进不了 `## Key check lines`

## symptom

`doc/evidence/v0.2.0/` 下七条 M2 证据的 `## Key check lines` 段，实际只
保留了**最先出现的那个 SVA 模块**（`axi_xbar_txlimit_sva`）的逐条行，
其余模块的 cover 命中数一条都没有。DV 修复卡验收要求报告
`axi_xbar_stall_sva` 的 6 条 cover 命中数变化时，发现这些数字**从来就不在
证据文件里**，只能回源 `sim/out/*.log` 取。

更危险的是截断**静默**：证据里看不到某条 cover，无法区分是
「这条 cover 不存在」还是「它被截断了」。里程碑签核时 rev 读证据会被误导。

## first_anomaly

signal: `doc/evidence/v0.2.0/*.log` 的 `## Key check lines` 段内容
time: n/a
how_found: DV 修复卡（BUG-0021 F1/F2/F3 + BUG-0023）执行验收项「报告 cover
命中数变化」时发现所需数字不在证据中。

## taxonomy

TOOL_ENV

## rca

1. `scripts/evidence.py` 的 `KEY_LINE_RE` 含 `match` 关键词。
2. `-assert verbose` 为**每一条** assertion/cover 打印一行
   （`"file", line: inst, N attempts, M match`），本仓库每次运行数百条。
3. 这些行全部匹配 `KEY_LINE_RE`，而 `KEY_LINES_MAX=30` 是一刀切的前 N 条。
4. 前 30 条被最先出现的模块整段占满 ⇒ 后面模块的数字被丢弃。
5. 丢弃处不留任何标记 ⇒ 截断不可见。

（框架 0.3.3 起新增的 2 条 `[FCOV_SUMMARY]` 明细行——即 FB-9 的修复——又把
3 条 txlimit 行挤出，进一步说明 30 条配额已经饱和。）

## fix

未派发（`scripts/evidence.py` 是 pinned snapshot，本地不可改——`make fw-check`
红线）。已按 CLAUDE.md §6 登记 `doc/fw-feedback.md` **FB-13** 回流框架，附三条
建议：(1) 关键行分类配额而非一刀切前 N 条；(2) SVA 逐条行按文件归并；
(3) 至少在截断处写 `... (K lines truncated)` 使截断可见。

本仓库侧在框架修复前的处置：**不追溯重写已登记证据**（同 BUG-0008 先例，
REV-004 裁决"不重写已签核产物"）。但里程碑签核时须知悉本条——见下
`## regression_guard`。

## rerun

不适用（未修复）。

## 对已登记证据判定有效性的影响

**判定本身不受影响**：`make evidence` 的接受判据是 `svacheck.judge` 两腿制
（UVM 记分板腿 + SVA 腿，fail-closed），两腿都读**源日志全文**而非摘要段。
摘要段只供人阅读。故七条证据的 PASS 结论仍然成立。

受影响的是**人工复核的可用性**：签核抽查若只读证据文件，会得到不完整的
SVA 图景。
