# BUG-0013 — §5.2.1 stall 的"接受边界"字面表述与基线 CUT_ALL_AX 弹性缓冲交互未蒸馏

> 状态：OPEN（SPEC_ISSUE，非阻塞，待 rev 仲裁）。本页为 in-progress 详情
> 页——`fix`/`rerun`/`regression_guard` 三段在仲裁前如实留白/记待办，非编造。
> 本页只陈述症状/事实，**不预判裁决结果与条款落点**（裁决权属 rev）。M2-OR01/
> OR02 的核心判据（响应不乱序，spec §5.2.3）不受影响、照常落地产证据——同
> BUG-0012 先例（非阻塞过渡处置）。

## symptom

M2-OR01 场景（同 slave 端口连发两笔低 `AxiIdUsedSlvPorts=3` 位相同、同方向、
目标不同 master 端口的事务）按 spec.md §5.2.1 字面表述构造 checker（"第二个
事务在第一个完成前不被接受...该 slave 端口的 AW/AR 通道被 stall"）：assert
第二笔的 `aw_valid&&aw_ready`（或 `ar_valid&&ar_ready`）不得在第一笔 B/rlast
完成前为真。仿真显示该 assert 在写方向、读方向均确定性失败——第二笔在第一笔
完成前即被外部接受：

```
[写] AW id=0x0 (bkt0,tgt0) accepted @115000ps
     AW id=0x8 (bkt0,tgt1) accepted @125000ps   <- 仅隔 1 拍，第一笔尚未完成
     B  id=0x0             @195000ps            <- 第一笔完成，晚于上一行
     B  id=0x8             @275000ps
[读] AR id=0x0 (bkt0,tgt0) accepted @285000ps
     AR id=0x8 (bkt0,tgt1) accepted @345000ps   <- 隔 6 拍（构造的间隔 5 拍
                                                    +1），第一笔仍未完成
     R  id=0x0             @365000ps            <- 第一笔完成，晚于上一行
     R  id=0x8             @445000ps
```

**关键旁证**：尽管"接受边界"字面判据被违反，**完成序（B/rlast 到达顺序）与
接受序完全一致**（B id=0x0 先于 B id=0x8；R id=0x0 先于 R id=0x8）——spec
§5.2.3 所述"AXI 要求同 ID 同方向事务的响应保序...故以 stall 方式防止跨
master 端口乱序返回"这一**功能目的**在仿真中被满足；scoreboard 的 M1 式
路由/数据判据（route/resp match）在同一次运行中全部通过、零 mismatch。

## first_anomaly

signal: `tb_top.gen_slv_stall_sva[0].u_axi_xbar_stall_sva`（`w_pend_vld`/
`w_pend_tgt` 状态 + `aw_valid&&aw_ready`）
time: 125000ps（写方向首次违反；读方向对应违反见 345000ps）
how_found: `make run TEST=m2_or01_stall_test SEED=1` 首次运行即在自研 SVA
（`tb/sva/axi_xbar_stall_sva.sv`）与 scoreboard（`tb/scoreboard_refmodel.sv`
C5.1/C5.2 段）两条独立判决路径上同时报告违反；怀疑自身 checker/激励构造有误
（CLAUDE.md §0 输入边界纪律），遂读 `vendor/axi/doc/axi_demux.md`
§Ordering and Stalls→Implementation 与 `vendor/axi/src/axi_demux.sv`/
`axi_demux_simple.sv` RTL 结构（仅为定位是自身激励缺陷还是 DUT/spec 交互，
未把观察到的 RTL 行为直接搬进 checker 期望值——CLAUDE.md 输入边界）：
- `axi_demux.sv` 在 `axi_demux_simple`（真正持有按 `AxiLookBits` 分桶计数器
  + 目标绑定寄存器的核心判决逻辑）**外面**包了一层 `SpillAw`/`SpillAr` 控制
  的 spill register（`i_aw_spill_reg`/`i_ar_spill_reg`），即 spec.md §7.2
  `LatencyMode=CUT_ALL_AX`（"AW/AR 各 2 拍"）落地处。
- spill register 提供弹性缓冲（skid-buffer 语义）：外部 slave 端口的
  `aw_ready`/`ar_ready` 反映的是**这层寄存器自身是否有空位**，不是
  `axi_demux_simple` 内部按 ID 分桶计数器/目标绑定寄存器的实时判决结果——
  第二笔请求可以在内部判决逻辑真正"看见"并比对第一笔之前，先被缓冲进这层
  寄存器，从外部观测点看就是"提前被接受"。
- 用临时 `$display`（已在交付前移除）核对 `w_pend_vld`/`w_pend_tgt` 与
  `aw_id`/`aw_hit`/`aw_tgt` 的实时取值，确认自研 SVA 的桶提取、目标译码均
  与 `axi_demux_simple.sv:217`（`slv_req_i.aw.id[0+:AxiLookBits]`，低位）
  一致——排除"用错高位/低位"这一自身实现错误的可能性。

## taxonomy

SPEC_ISSUE

spec.md §5.2.1 的表述（"该 slave 端口的 AW/AR 通道被 stall"）蒸馏自
`axi_demux.md` §Ordering and Stalls 的"边界层"叙事（"it will not accept the
second transaction"），但未与同一来源文档同样记载的 `SpillXX` 缓冲层
（`axi_demux.md` §Configuration 表 `SpillXX` 行 + spec.md §7.2 `CUT_ALL_AX`
钉定值）交叉核对：`axi_demux.md` 描述的"不接受"是 `axi_demux_simple` 核心
判决逻辑的行为，而 `axi_demux.sv`（真正例化进 xbar 的模块）额外包裹的 spill
register 层，在基线 `CUT_ALL_AX` 下正好打开，会在核心判决逻辑之前提供弹性
缓冲——两处来源本身不冲突（均为许可来源文档记载的事实），是 arch 蒸馏 spec.md
§5.2.1 时未合并这两处关联叙事，导致"接受边界"字面表述与基线延迟配置的实际
交互未被蒸馏、旁落为本条 SPEC_ISSUE。非 DUT_BUG（RTL 行为与两处来源文档各自
的字面描述均不矛盾，是文档蒸馏遗漏的组合效应）；非 TB_BUG（bucket/译码等
自身实现已核对一致，见 first_anomaly）。

## rca

1. spec.md §5.2.1 蒸馏自 `axi_demux.md` §Ordering and Stalls→Implementation
   的核心判决逻辑叙事（"gets an AW or AR...indexes the counters...stalls"）。
2. 同一文档 §Configuration 表另记载 `SpillXX`（"Inserts one spill register on
   the respective channel...before the demultiplexer"）——**在核心判决逻辑
   之前**；spec.md §7.2 把 `LatencyMode=CUT_ALL_AX` 钉定为"AW/AR 各 2 拍"，
   即该 spill register 被启用。
3. `axi_demux.sv` 的实际结构验证了 (2)：`i_aw_spill_reg`/`i_ar_spill_reg`
   夹在外部 slave 端口与 `axi_demux_simple`（持有 §5.2.1 判决逻辑的模块）
   之间，提供 skid-buffer 式弹性缓冲。
4. §5.2.1 的蒸馏未合并 (2)/(3) 所属的缓冲层交互，字面表述隐含"外部边界即时
   可观测"，与基线配置下的实际弹性缓冲窗口不一致。
5. spec.md §7.4"延迟不敏感"原则声称 `LatencyMode`/`PipelineStages`"不改
   功能响应"，但未明确"功能响应"在此是否包含"接受边界的即时性"——本条
   即该未言明边界的一个具体交互实例（功能目的 §5.2.3 保序仍然满足，见
   symptom 的完成序旁证）。

## fix

**REV-006 裁决 = SPEC_CHANGED（采候选 (a)）。** state 留 OPEN；spec 正文编辑 +
sha256 重 pin + 状态转 SPEC_CHANGED 由 orch 应用（同 REV-005 先例，非 rev 落笔）。
裁决全文与三处精确编辑范围见 `doc/review/REV-006.md` §2.2/§3。

**裁决要点**：
- **采 (a)**：收窄 §5.2.1"接受边界"字面为"第二笔在第一笔完成前**不被转发到其
  目标 master 端口**、判决锚点落 §5.2.3 完成序不乱序"；§7.4 增第 5 条把"接受/
  拒收边界即时性"通用归入延迟不敏感表现；§5.4.3 挂交叉指针。
- **驳回 (b)**，两条独立理由：(1) DUT 在基线 `CUT_ALL_AX` 下确实把第二笔接受进
  spill register 且功能正确（响应保序满足），按 (b) 写的 assert 会在功能正确、
  与两处许可来源字面均相符的 DUT 上确定性**假红**；(2) 许可来源无任何"接受边界
  须即时"或"弹性缓冲窗口深度须受约束"条款，落 (b) 须**发明无来源条款**=behavior
  leak，rev 必须驳回。
- **来源核验（rev 亲验，REV-006 §1）**：xbar.md L86 自陈 stall 功能目的是"不把
  第二笔 forward 到不同 master 端口以避免响应乱序"（"accept"=forward 进交换
  网络）；demux.md L31 "spill register ... before the demultiplexer"/L37 不损
  吞吐；`axi_demux.sv` L89-209 结构证实 `i_aw_spill_reg`/`i_ar_spill_reg` 夹在
  外部 slave 端口与 `axi_demux_simple` 之间、`slv_resp_o.aw_ready`=spill 自身
  空位而非核心判决 ready。taxonomy（SPEC_ISSUE、非 DUT_BUG/非 TB_BUG）核验成立。

**orch 应用范围（三处编辑，精确"原文/新文/理由/落点"见 REV-006 §3）**：
1. §5.2.1 第 1 条：收窄字面表述 + 加"接受边界即时性说明"。
2. §7.4 增第 5 条：接受/拒收边界即时性 = 延迟不敏感表现（通用化，同时覆盖
   §5.2 stall 与 §5.4.3"达到上限即拒收"）。
3. §5.4.3 MaxMstTrans 侧句尾加交叉指针（指向 §7.4.5）。
§5.2.3 正文无需改动（编辑 1 已交叉引用之）。

**DV 过渡处置经核验、升格为定案**：`tb/scoreboard_refmodel.sv`（C5.1/C5.2 段，
L271-307）与 `tb/sva/axi_xbar_stall_sva.sv`（L205-216）以"完成序不乱序"为判决门
——与裁决 (a) 的最终锚点**一致**，本裁决把该过渡门升格为长期判决门；"接受边界"
字面判据（`stall_sva.sv` L233-241 cover property）**维持为 cover、不得升格为
assert**（该读法无许可来源，REV-006 §2.2）。无需改写现有判决逻辑，仅需按 spec
编辑落地后更新条款引用。
