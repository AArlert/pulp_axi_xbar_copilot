# BUG-0020 — 仿真从不产 FSDB，xdebug 波形因果能力在本仓库无法使用

## symptom

CLAUDE.md §4 规定「DV/REV 但凡涉及失配定位……应先用 xverif 工具体系做确定性
查询」，其中波形/RTL 因果维度的入口是 `xdebug`。实际调用即失败：

```
@xdebug.error.v1
action: session.open
code: SESSION_UNHEALTHY
message: Server did not become ready: child_exited
```

即本仓库**没有任何可供 xdebug 打开的波形**，`session.open` 只能给
`daidir`（静态设计信息），而 NPI 初始化在这种输入下失败。

后果：本仓库当前配置下，任何需要"回到波形看实际发生了什么"的溯因工作
（BUG-0018 那类观测相位问题是典型）都没有波形可查，只能退回日志推理——
与 CLAUDE.md §4「优先用 xverif 取事实，而非纯模型推理/手算」的纪律冲突。

## first_anomaly

signal: `has_fsdb` = false（xdebug engine 的 `server.transport_config` 阶段）
time: 2026-07-28T11:38:02.983+1000（engine lifecycle 记录）
how_found: orch 在 BUG-0017（xcov 不可用）之后逐工具实测 xverif 工具体系，
对 `out/simv.daidir` 调 `xdebug session.open` 失败，取
`~/.xdebug/engine/sessions/<id>/logs/lifecycle.ndjson` 定位到 NPI init 阶段。

## taxonomy

## rca

engine lifecycle 日志给出决定性对照——**同一台 VM、同一个 Verdi 安装**：

```jsonc
// 本仓库，2026-07-28（失败）
"phase":"server.transport_config"  "has_daidir":true, "has_fsdb":false
"phase":"npi_init.begin"
"phase":"npi_init.failed"          // 25ms 后失败，child 以 status 256 退出

// 姊妹仓库 ppa-lite-copilot，2026-07-09（成功）
"phase":"ensure_session.success"   "fsdb":".../ppa-lite-copilot/sim/out/wave.fsdb", "dbdir":""
```

1. `xdebug-engine` 是 C 二进制，链接 Verdi 的 **C API** `libNPI.so` /
   `libnpiL1.so` / `libvfs.so`——`ldd` 全部解析成功，**不经过 BUG-0017 的
   `pynpi` 路径**，故本条与 Verdi 版本无关。
2. 其 NPI 初始化需要 FSDB；只给 `daidir` 而无 `fsdb` 时 `npi_init` 失败。
3. 本仓库 `sim/Makefile` **没有任何目标产生 FSDB**：`verdi:` 目标引用了
   `$(OUT)/wave.fsdb`，但该文件从不被生成；`sim/out/run.ucli` 的全部内容
   是 `run; exit`，无 `fsdbDumpvars`；编译旗标里也没有对应的 dump 配置。
4. 故 xdebug 在本仓库不可用的原因是**项目侧缺口（不产波形）**，而非环境
   能力缺失——2026-07-09 的成功记录证明该 VM 上 xdebug 可正常工作。

## fix

`sim/Makefile`：可选波形路径 `FSDB=1`（变量名沿用 `scripts/make/vcs-2018.mk`
里早已预留的 `FSDB ?= 0`）。commit: <pending>

`run:` 在 `FSDB=1` 时生成 `$(OUT)/wave.ucli`
（`call {$fsdbDumpfile(...)}` + `call {$fsdbDumpvars(0, tb_top)}` + `run` +
`exit`）并以 `-ucli -i` 驱动 simv；UVM 与上游 sanity 两条路径共用同一段。

**默认路径零成本**（对照实验，同一 warm 状态下 A=改前 Makefile / B=改后）：

| | warm `make run` 用时 | log 字节 | wave.fsdb |
|---|---|---|---|
| A（改前） | 0.90 / 0.90 s | 29464 | 无 |
| B（改后 FSDB=0） | 0.90 / 0.89 / 0.90 s | 29464 | 无 |

`FSDB` 不出现在 `compile:` 里，编译旗标逐字不变（`-debug_access+all -kdb`
与 Verdi PLI 本就常开），故 `FSDB=1` 不触发重编、也不改变默认产物；
默认路径 simv 命令行与改前的差异只有 `$(UCLI)` 空展开留下的一个空格。
`FSDB=1` 单次运行：1.05 s、`wave.fsdb` 345 KB。

**第二道墙（本卡另一发现）**：产出 FSDB 后 `xdebug session.open` **仍**失败
（`has_fsdb:true` 但 `npi_init.failed`）——原因在环境而非项目：xdebug engine
的 NPI 初始化要求 `VERDI_HOME` + `VCS_HOME` + `LM_LICENSE_FILE` 三者有值，
且 `LD_LIBRARY_PATH` **恰为** `$VERDI_HOME/share/PLI/VCS/LINUX64`；尾部空元素
（`...LINUX64:`，即 `LD_LIBRARY_PATH := ...:$(LD_LIBRARY_PATH)` 在父变量为空时
的展开形态）同样导致 `npi_init.failed`。逐项对照实测：缺 `LM_LICENSE_FILE`
失败、缺 `VCS_HOME` 失败、带尾冒号失败；四项齐备即
`ensure_session.success`。调用方式已记入 `sim/Makefile` `verdi:` 上方注释。

边界不变（CLAUDE.md §4）：波形只用于观测"实际发生了什么"，checker 的期望值
仍只从 `doc/spec.md` 推导。

    LD_LIBRARY_PATH=/home/synopsys/verdi/Verdi_O-2018.09-SP2/share/PLI/VCS/LINUX64 \

#            "target":{"fsdb":"<abs>/sim/out/wave.fsdb"},"args":{"name":"xw0"}}

`~/.xdebug/engine/sessions/<id>/logs/lifecycle.ndjson` 含
