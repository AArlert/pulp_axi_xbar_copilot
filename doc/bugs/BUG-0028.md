# BUG-0028 — `regress.list` 长期缺 7 个 M2 场景，回归门禁不覆盖 M2

## symptom

`sim/regress/regress.list` 在本卡之前只有 3 条（`upstream_sanity` +
`m1_01_smoke_test` + `m1_02_id_prefix_test`）。M2 的七个场景
（CFG01/OR01/OR02/TL01/TL02/WO01/AT01）自 2026-07-28 落地起**从未进入回归
清单**——`make regress` 报 3/3 PASS，看起来一切正常，实际上整个 M2 的判决链
从未被回归门禁覆盖过。

即：回归绿灯的**范围**远小于它给人的印象。

## first_anomaly

signal: `sim/regress/regress.list` 的行数（3 而非 10+）
time: n/a
how_found: DV 卡（M2-OR03 落地）执行"全回归无伤"验收项时，发现
`make regress` 只跑 3 条，遂比对 testplan 已 ✅ 的场景清单。

## taxonomy

TB_BUG

（回归配置缺口。归 TB_BUG 而非 TOOL_ENV：`make regress` 与 `regress.py`
工作正常，缺的是我们自己该往清单里填的行。）

## rca

1. M0 期建立 `regress.list` 时只有 `upstream_sanity` 一条。
2. M1 里程碑签核前补入 M1 两条（见 0.1.2 closeout 记录）——**那次是人工
   想起来补的，不是任何机制提示的**。
3. M2 七个场景各自落地时，DV 卡的验收标准都是"本场景 PASS + `make evidence`
   登记"，没有任何一条要求"同时入回归清单"。
4. 于是七个场景全部合规落地、全部有 PASS 证据，而回归清单一行未增。
5. `make regress` 因此持续报"3/3 PASS"——**分母静默缩水，绿灯照常**。

与 BUG-0022（lint 增量假绿）、FB-11/FB-12/FB-14 是同一族失效模式：
**通过信号的覆盖范围与它给人的印象不符**，且没有任何机制让这个差距可见。
差别在于前几条是"检查没执行却报通过"，本条是"检查执行了但只覆盖了一小部分"。

## fix

已修（DV M2-OR03 卡同批）：`sim/regress/regress.list` 补入 8 条
（7 个 M2 场景 + 新增的 `m2_or03_guard_test`），`make regress` 由 3/3 变
**11/11 PASS**，摘要登记于 `doc/evidence/v0.2.0/result_summary.txt`。

**本条的真正修复不止于补行**——补行只是把当下的缺口填上，不能防止 M3/M4
重演。见 `## regression_guard`。

## rerun

`make regress` → 11/11 PASS（`sim/result_summary.txt` /
`doc/evidence/v0.2.0/result_summary.txt`，2026-07-28）。

**复验待非修复方执行**（closer ≠ fixer：补行的是 DV M2-OR03 卡）。复验内容：
独立跑一次 `make regress`，确认 (a) 分母为 11、(b) 全 PASS、(c) 清单覆盖
testplan 中全部已 ✅ 的场景。

## regression_guard

type: checklist
paths: sim/regress/regress.list, doc/testplan.md
note: **补行不是守卫**。真正的守卫是一条"清单完整性"检查——回归清单必须
覆盖 `doc/testplan.md` 中每一条状态为 ✅ 的场景，两者的差集非空即失败。
在该检查落地前，替代约束：任何 DV scenario 卡的收版清单里必须包含"本场景
已入 `regress.list`"一项；里程碑签核时须人工核对清单与 testplan ✅ 行的
差集。另：本条与 BUG-0022 共享同一个教训——**看到绿灯要先问它覆盖了什么**，
`make regress` 的 "N/N PASS" 里那个分母是自己填的。
