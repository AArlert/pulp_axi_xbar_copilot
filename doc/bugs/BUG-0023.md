# BUG-0023 — `axi_xbar_stall_sva.sv` 跟踪表同沿写冲突，新事务 open 记录被吞（漏检/假绿侧）

## symptom

`tb/sva/axi_xbar_stall_sva.sv` 的保序跟踪表在同一时钟沿同时发生
"AW 握手（登记新事务）"与"B 握手（注销完成事务）"、且两者 ID 相同时，
后写的 B 分支覆盖先写的 AW 分支：

```systemverilog
// L129-142 结构（示意）
if (aw_valid && aw_ready)  w_id_open[aw_id] <= 1'b1;   // 先：登记新事务
if (b_valid  && b_ready)   w_id_open[b_id]  <= 1'b0;   // 后：注销完成事务
```

`aw_id == b_id` 时，新事务的 `open` 记录被静默吞掉。此后该 ID 的乱序检查
对这笔事务**永久失效**——它从未被登记，因此也永远不会被检出乱序。

读侧 `r_id_open` 同构。

**方向是漏检（假绿侧）**：该缺陷不会造成假红，只会让本该被检出的乱序
悄无声息地通过。这与 BUG-0021 分诊出的 F1（判决 property 内调函数，
只造假红）方向相反，两者必须分开处置。

## taxonomy

TB_BUG

## rca

1. 跟踪表用单个 `always_ff` 块内的多条条件赋值维护，AW 分支在前、
   B 分支在后。
2. SystemVerilog 过程块内对同一变量的多次非阻塞赋值，**最后一次生效**
   （IEEE 1800 §10.4.2）。
3. 同沿 `aw_id == b_id` 时两个分支同时为真 ⇒ B 分支的 `<= 1'b0` 生效，
   AW 分支的 `<= 1'b1` 被丢弃。
4. 该 ID 的新事务因此从未进入在飞集合，后续任何针对它的乱序判据都不会
   触发（`w_id_open[cand]` 恒为 0 ⇒ 候选集不含它）。
5. **同族对照证明这是遗漏而非有意**：`tb/sva/axi_xbar_atop_sva.sv:113-120`
   对同一模式做了**显式互斥保护**。两处出自同一设计意图，只有一处写了
   保护 ⇒ 另一处是疏漏。

## fix

commit: <待 orch 回填>
what: `tb/sva/axi_xbar_stall_sva.sv` 的两条注销分支加同沿互斥保护——本沿已
登记同一完整 ID 时，注销让位（`atop_sva.sv:113-120` 的现成形态）：

```systemverilog
if (b_valid && b_ready
    && !(aw_valid && aw_ready && aw_hit && (aw_id == b_id)))
  w_id_open[b_id] <= 1'b0;
if (r_valid && r_ready && r_last
    && !(ar_valid && ar_ready && ar_hit && (ar_id == r_id)))
  r_id_open[r_id] <= 1'b0;
```

净效果 = "旧的关掉、新的开着"，与同一 `always_ff` 内 `w_id_tgt`/`w_id_seq`
被新事务覆写的语义一致（那两项本就无条件按新事务写）。读侧同构一并处理。

证伪（VCS O-2018.09-SP2 上的最小复现，把同一 `always_ff` 内的两种写法并排）：
同沿 `set+clear` 打在同一元素上 → `open_bad=0`（当前写法，登记被吞）
vs `open_fix=1`（加保护后，登记存活）。
