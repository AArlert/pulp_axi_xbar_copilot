# BUG-0022 — `make lint` 增量编译命中时假绿：门禁不区分"真干净"与"根本没 lint"

## symptom

同一份代码，连跑两次 `make lint TEST=m2_cfg01_reconfig_test`：

```
第 1 次（强制重编）：../tb/ 范围命中 259 条 Lint 告警 → exit 2
第 2 次（增量命中）：lint clean within ../tb/ scope      → exit 0
```

代码一个字节都没改，门禁结论却从"不合格"翻成"合格"。

第 2 次 VCS 打印 `The design hasn't changed and need not be recompiled.`
并把 `sim/out/lint.log` **覆写**成一份不含任何 `Lint-[...]` 行的短日志；
`sim/Makefile` 的过滤逻辑（`grep -A1 '^Lint-\[' $(OUT)/lint.log | grep -qE '^\.\./tb/'`）
在这份空日志上自然一无所获，于是输出 `lint clean within ../tb/ scope` 并
返回 0。

即：门禁把"这次根本没有执行 lint"**误判为**"lint 干净"。

## first_anomaly

signal: `sim/out/lint.log`（增量命中时被覆写为不含 Lint 行的短日志）
time: n/a（编译期）
how_found: DV 分诊卡（BUG-0021）执行 min_repro 时，第一次调用即命中——
增量编译使门禁给出假绿；删除 `sim/out/simv_lint.daidir/.vcs.timestamp`
强制重编后才复现出 259 条。三次复跑确认稳定。

## taxonomy

TB_BUG

（门禁自身的判据缺陷。归 TB_BUG 而非 TOOL_ENV：VCS 的增量编译行为本身
是正常且有意的，缺陷在于 `sim/Makefile` 的判据把"日志里没有 Lint 行"
无条件等同于"lint 通过"，未校验这次是否真的执行了 lint。）

## rca

1. `sim/Makefile` 的 `lint:` 目标以 `$(OUT)/lint.log` 中是否存在
   `^Lint-\[` 且紧邻行落在 `^\.\./tb/` 作为唯一判据。
2. VCS 在设计未变时走增量路径，不重新分析源码、**不产生任何 `Lint-[...]`
   行**，但仍以 `-l $(OUT)/lint.log` 覆写日志文件。
3. 于是"lint 未执行"与"lint 执行且干净"在日志上呈现为同一形态——
   两者都是"没有 Lint 行"。
4. 判据无法区分二者，取了乐观的一侧 ⇒ 假绿。

这与 `workflow/discipline.md` rule 2 的 gate 例外条款正面相关：门禁是产品
本身，而一个会假绿的门禁比没有门禁更危险——它给出未经验证的通过信号。

## fix

`sim/Makefile`：把原 `lint:` 拆成 `lint-run:`（执行 + 自证）与 `lint:`（判据，
过滤逻辑逐字未改），并新增 `lint-diff:`（BUG-0021 守卫的机械入口）。
commit: <pending>

`lint-run:` 加两道防线：

- **(a) 强制全量重编**：VCS 前 `rm -f $(OUT)/simv_lint.daidir/.vcs.timestamp`，
  从源头消灭增量命中。
- **(b) 逐文件执行证明**：核对本次日志里 `../tb/` 下**每一个** `.sv`
  （`LINT_SRCS := find ../tb -name '*.sv'`，含 `include`-d class 文件）都出现过
  `Parsing design file` / `Parsing included file`；缺一即 `[LINT-GATE][FAIL]`
  退出 1，并声明"本次结论作废"。

(b) 不是 (a) 的冗余，它多堵两条路：① (a) 失效时（VCS 换 timestamp 位置、
或有人删掉那行）仍报红——实测把 `rm` 抽掉后确实由 (b) 逮住；② **分母缩水**：
从 `flist/tb.f` 摘掉某个 tb 源文件（BUG-0021 红线明令禁止的"变绿"手法）会让
它落在 lint 范围外，(b) 逐文件核对直接报红。判据只增不减，`../tb/` 过滤范围
未动（对照实验：干净树上 vendor 的 240 条告警仍被正确排除在判定外）。

副产品（符合 BUG-0021 守卫"任何 lint 通过的说法都须附带它跑的是哪个 flist"）：
`make lint TEST=upstream_sanity` 过去输出误导性的 `lint clean within ../tb/
scope`，现在因 0/20 文件被分析而**报红**。根 `make lint`（默认 TEST=
upstream_sanity）随之从"假绿"变为"loud fail"，须显式带 UVM TEST。

注：卡片建议的执行实证标记 `elaboration done` 在 VCS O-2018 日志里**不存在**
（`grep -ci "elaboration done"` = 0）；全程唯一的整体标记是末尾的
`CPU time: ... to compile + ... to elab + ... to link`，但它只证明"编译发生过"、
不证明"你关心的文件被分析过"，故未采用。
