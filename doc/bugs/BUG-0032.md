# BUG-0032 — err_slv 对 ATOP（尤其要求读响应的原子操作）的应答形态，许可来源未定义

## symptom

M3 错误路径场景设计时浮出：一笔 `aw.atop != '0` 且**要求读响应**的原子操作
（atomic load），其地址若不匹配任何 rule 且该 slave 端口未使能 default master
port，将被路由到本端口的内部 decode error slave（spec §4.2）。此时期望的应答
形态在许可来源中**没有答案**：

- spec §4.3 只按"读事务 / 写事务"两分：**写**事务在收齐整个 W burst 后返回
  **单拍 B**（DECERR）。原子读是由 AW 发起的写侧事务，按该条字面只该得到一拍 B。
- spec §6.3 则要求原子读 **B 与 R 两个通道都返回响应**。
- 两条都成立时，err_slv 是否也要为这笔 AW 产出一串 R beat（几拍？`AxLEN+1`？
  数据是否同为 `32'hBADCAB1E`？响应码 DECERR？）——**无条款可推**。

若不作定义，checker 只能"现场解释"，而两种解释（只回 B / 回 B+R）都会让对方
形态判为失配。这正是 spec §0 行 6 禁止的情形。

## taxonomy

SPEC_ISSUE

## rca

1. spec §4 的应答形态按"读/写"二分蒸馏自 xbar.md 的 "proper number of beats"
   一句，该句写于只有 AXI4 读写两类事务的语境。
2. spec §6 的 ATOP 条款蒸馏自 demux.md §Atomic Transactions，该节只谈 demux 的
   路由/计数器注入，不涉及 err_slv。
3. 两节各自完备，交集（ATOP × 译码未命中）无任何一方覆盖 ⇒ 缺口不是蒸馏遗漏，
   而是**上游文档本身没写**。
4. 该缺口在 M0-M2 不可触达（全部场景为译码命中路径，且 ATOP 只在 M2-AT01 出现、
   地址命中）；M3 的主题是错误路径，一旦 env 允许 ATOP 落在未命中地址即触达。

## fix

未派发。**arch 侧不作现场解释**（spec §0 行 6 / discipline rule 1）。
处置按本仓库既有先例（spec §6.2 的 `ATOPs=0` 无-ATOP 约束、§8.3 的稀疏
`Connectivity` 地址表约束）：以 **env 构造性约束**使该情形不可触发，缺口本身
列为**上游确认项**，不阻塞 M3。

env 约束（已写入 `doc/testplan.md` M3-DE01 行与 `doc/design-prompt/uvm_env.md`
§6 C6.2）：**M3 全部场景不向译码未命中地址发起任何 ATOP**（送往未命中地址的
AW 恒 `aw.atop ≡ '0`）。

若将来需要覆盖该组合（例如 M4 覆盖率收敛发现 `axi_err_slv` 的 ATOP 相关分支
未被激励），须先走 rev 仲裁补 spec 条款，再解除本约束——**不得**由 DV 在
checker 里二选一。
