# BUG-0011 — `MaxSlvTrans` 执行机制在许可来源中无机制级依据

> 状态：OPEN（SPEC_ISSUE，待 rev 仲裁）。本页为 in-progress 详情页——
> `fix`/`rerun`/`regression_guard` 三段在仲裁前如实留白/记待办，非编造。
> 本页只陈述症状/事实与来源缺口，**不预判裁决结果**（裁决权属 rev）。

## symptom

`MaxSlvTrans`（基线 =6，"每 master 端口每 ID 在飞事务上限"）在许可来源中缺乏
执行机制描述，M2-TL02 checker 的精确判据无法从 spec 推导：

- spec.md §5.4.2「每 master 端口每 ID in-flight 事务数 ≤ `MaxSlvTrans`」与 §5.4.3
  「达到上限时对应端口不再接受新事务」只声明了**存在上限 + 概括性反压**，未给
  分组维度与触发点。
- 结构上负责 master 端口侧的下层部件是 `axi_mux`（`axi_xbar` 每 master 端口例化
  一个），但 `vendor/axi/doc/axi_mux.md` 全篇**没有**与 axi_demux.md 那类
  "按 ID 桶计数、封顶即拒收"对应的段落。axi_mux.md 参数表里唯一相关的
  `MaxWTrans` 语义不同：它是「AW→W 通道间保存 ID 高位的 FIFO 深度」（作用对象是
  整个 mux 的未完成 AW 队列，而非"单一 ID 的事务计数上限"）。
- 附加口径缺口：xbar.md §Configuration 表 `MaxSlvTrans` 行写「per ID」，而
  axi_pkg.sv L492-494 同字段注释「each slave connected to the crossbar ...
  in flight」**未提 per ID**——两处顶层来源本身对"是否按 ID"就不完全一致。

即：许可来源确认了上限的**存在**与"每 ID"限定（xbar.md），却无任何来源描述它
**如何**执行（哪个子模块、按什么分组、是否硬性反压）。

## first_anomaly

非仿真发现（静态比对，未跑仿真）。M2 场景规划时，为 `MaxSlvTrans` 上限场景
（testplan M2-TL02）推导 checker 判据，逐一检查许可来源：

- spec.md §5.4.2/§5.4.3；
- xbar.md §Configuration 表 `MaxSlvTrans` 行 vs axi_pkg.sv L492-494 注释（发现
  "per ID" 只在前者出现）；
- `vendor/axi/doc/axi_mux.md` 全文参数表 + 正文（发现无按 ID 分桶的事务计数
  机制描述，仅有语义不同的 `MaxWTrans`）。

三处比对后确认：master 端口侧上限的执行机制在许可来源中无处可溯，即本条。

## taxonomy

SPEC_ISSUE

许可来源不定义该参数的执行机制：主文档 xbar.md 与 axi_pkg.sv 仅述其存在与
（xbar.md 侧的）"每 ID"限定，未述机制；结构上负责该端口侧的子模块文档
axi_mux.md 无对应计数器描述。**禁止读 axi_mux.sv/axi_xbar.sv 实现体作补充**
（spec-from-RTL 红线）。非 DUT_BUG（无波形/证据）、非 TB_BUG（尚无 checker）、
非 TOOL_ENV。

## rca

1. `MaxSlvTrans` 的存在与"每 ID"限定来自 xbar.md §Configuration 表顶层一行
   （"Each master port can have at most this many transactions per ID in flight"）
   + axi_pkg.sv 注释（后者未提 per ID）；spec.md §5.4.2 据此蒸馏。
2. spec.md §5.4.3 的"达到上限对应端口不再接受新事务"是由"至多 in flight"语义
   + AXI 握手反压**推导**的概括表述（§5.4.3 本身已标注此为推导，非直接来源），
   而非某条来源明文。
3. 与 `MaxMstTrans`（demux 侧有 Implementation 小节给出分桶计数机制，见 BUG-0010）
   不同，master 端口侧的 axi_mux.md 没有任何对应的机制小节——精确分组维度
   （是否真按前缀后完整 ID 分桶）、是否存在硬性反压、触发点，均无来源可依。
4. 因此 M2-TL02 checker 若要断言"第 7 笔被拒收"这类精确行为，其期望值只能来自
   实现体（被红线禁止）或来自尚不存在的 spec 条款——故 checker 落地前必须先由
   rev 裁决补齐来源（或转上游确认）。

## fix

**REV-005 仲裁裁决（2026-07-27）：SPEC_CHANGED —— 保上界为规范 + 机制列上游确认
+ 解锁弱化 checker（三段式，非 arch 提案的二选一）。**

rev 独立核验许可来源原文：xbar.md L47（`MaxSlvTrans` = "Each master port can have
at most this many transactions **per ID** in flight"，上界**存在**且含"per ID"）；
axi_pkg.sv L492-494（同字段注释**未提 per ID**）；`axi_mux.md` 全文（结构上负责
master 端口侧的子模块）**无任何**按 ID 分桶的事务计数机制段落，`MaxWTrans`（L29）
语义不同（AW→W ID 前缀 FIFO 深度）。即：上界的**存在**与"per ID"可溯（xbar.md），
但**执行机制**（子模块/分组维度/是否硬性反压/触发点）在许可来源无处可溯；读
axi_mux.sv/axi_xbar.sv 补齐属 spec-from-RTL 红线（禁）。

**裁决三段**：
1. **§5.4.2 的可观测上界保留为规范**——"每 master 端口、每（master 端口侧可观测
   的前缀后）ID、在飞事务数 ≤ `MaxSlvTrans`"是 xbar.md L47 的近逐字重述，可证伪
   （监视计数、>6 即红）；**"per ID" 采 xbar.md 口径**（over axi_pkg 省略，同
   BUG-0005 精神：主文档更具体读法胜过较含糊源码注释）。
2. **§5.4.3 的机制主张须限定**——现"达到上限对应端口不再接受新事务"对 MaxMstTrans
   有 demux.md L74 支撑，但对 **MaxSlvTrans 无来源**，须标注其执行机制在许可来源
   未定义、列为**上游确认项**（同 BUG-0004/0002 先例，不阻塞里程碑）。
3. **解锁 M2-TL02 弱化 checker**——可落地一条**保守可观测上界监视器**（分组见
   ## regression_guard 的不假红约束），但**不得**断言机制级"第 7 笔在某具体通道/
   时点被拒收"。

**orch 应用范围**（rev 只出裁决，spec 编辑 + 重 pin + 本 bug 状态转 SPEC_CHANGED
由 orch）：§5.4.2 保留（可补"per ID = master 端口侧可观测前缀后 ID、采 xbar.md
口径"澄清）；§5.4.3 加"MaxSlvTrans 执行机制许可来源未定义 + 上游确认项"标注；
依据栏记 xbar.md L47 + "axi_mux.md 无机制段落"缺口 + BUG-0005/0004 先例。详见
`doc/review/REV-005.md` §3。
