# BUG-0073 — nested `make` inside an evidence CMD leaks directory-banner noise, breaking `tail -N`-based signatures

## symptom

A non-sim `make evidence BUG=... CMD='make <target> ...' EXPECT=...`
signature that nests another `make` invocation inside `CMD` and pipes its
output through `tail -N` (a natural way to grab "the target's own last
line", e.g. `make guards FILES=... 2>&1 | tail -1`) can silently capture
GNU Make's own `Entering/Leaving directory` banner instead of the target's
real last line — because the nested `make` subprocess, running as a child
of the `make evidence` recipe, inherits enough of the outer make's
environment to print those banners, and they land *after* the target's own
output.

## taxonomy

TOOL_ENV — result (the captured stdout's last line) changes with the

## rca

```
observed:   `make guards FILES=... 2>&1 | tail -1` gives "1 guard(s)
            matched" run directly, but "expected signature ... not found"
            when the same string runs as a `make evidence` CMD
first_anomaly: a probe CMD (`P=$(mktemp); make guards FILES=... > "$P"
            2>&1; cat "$P"`) run through `make evidence` shows the
            captured output framed by `make[1]: 进入目录"..."` /
            `make[1]: 离开目录"..."` — the leaving-directory line is last,
            not the guard-count line
anomaly:    the same literal CMD string produces different stdout shapes
            depending on whether it is typed directly or executed as a
            child of a `make evidence` recipe
chain:      `scripts/evidence.py --cmd` runs `subprocess.run(args.cmd,
            shell=True)` — that subprocess is itself a child of the `make
            evidence` recipe -> when `args.cmd` contains a nested `make
            <target>` call, that nested make detects it is running as a
            sub-make (via inherited MAKEFLAGS/MAKELEVEL) -> GNU Make's
            standard behavior for a detected sub-make is to print
            Entering/Leaving-directory banners around its output -> a
            direct top-level shell invocation of the identical string has
            no such inherited make state, so it never prints these banners
            -> `tail -1` (or any other last-line-position-dependent
            extraction) silently picks up the wrong line under one
            invocation path but not the other, and the person writing the
            CMD has no reason to expect this divergence when hand-testing
            it in a plain shell first
class:      TOOL_ENV (invocation-path-dependent stdout shape, no
            correctness defect in the guarded target itself)
guard:      see ## regression_guard — prefer `grep` for a distinctive
            substring over positional (`tail -N`/`head -N`) extraction
            whenever a CMD nests another `make` call
```

A closely related, independently-triggered observation from the same
diagnostic session (not the primary defect above, but sharing the same root
class and worth recording so a future closer does not re-discover it from
scratch): GNU Make automatically exports command-line-defined variables
(here, `EXPECT=...`/`CMD=...`/`BUG=...`) into the environment of the
recipe's child processes. A CMD that happens to dump `env` for diagnostic
purposes will see these self-referential variables in its own output; if
their literal text happens to contain the `EXPECT` substring being searched
for, `scripts/evidence.py` can register a false-positive match. This card's
own diagnostic probe hit exactly this shape once (see `## fix`) — no
previously-registered evidence was affected (the accidental overwrite
targeted a `.log` this same card was actively regenerating, caught and
corrected before the card closed).

## fix

commit: none yet — filed OPEN. Worked around inline for this card's own 15
evidence signatures (switched every guard-consumption CMD to `grep
"guard(s) matched"` instead of `tail -1`; avoided any `env`-dumping probe
CMD in a registered signature).
what (this card's incident, for the record): while diagnosing this bug, a
throwaway probe CMD registered against `BUG-0072` (chosen because it was
already correctly closed and the probe's `EXPECT` was designed to *not*
match) accidentally matched via the exported-`EXPECT`-variable mechanism
described above, overwriting `doc/evidence/v0.4.40/BUG-0072.log` with the
probe's diagnostic output instead of BUG-0072's real KILL-proof content.
Caught immediately (the log's own content made the mismatch obvious);
`doc/evidence/v0.4.40/BUG-0072.log` was regenerated in place by re-running
BUG-0072's original, correct `make evidence` command
(`python3 scripts/docsx.py --kill-proof`), restoring byte-for-byte the
intended KILL-proof excerpt. `doc/bugs.md`'s BUG-0072 row was not affected
(status/verify_evidence values were identical before and after, since the
row already pointed at the same path).

## regression_guard

note: no mechanized guard yet (the fix itself is undecided — see `##
fix`/`verify_evidence` candidates). Interim, non-mechanized guard: any
future evidence CMD that nests a `make <target>` invocation should extract
its signal with `grep` for a distinctive substring, never a positional
`tail -N`/`head -N` (which silently changes meaning depending on whether
GNU Make's own Entering/Leaving-directory banners are present); a CMD that
dumps raw `env` for diagnostic purposes should never be registered as a
real evidence signature (self-referential make variables can leak into it).
Not yet migrated into `doc/guards.md`'s structured table — out of card 2e's
declared scope (a batch bug-closer card, not a fixer card); a future fixer
card should register it there once the fix itself lands.
