# BUG-0024 — `w_id_open` 是单 bit 而非计数器，同 ID 合法重叠时跟踪记录被提前清除（漏检）

## symptom

`tb/sva/axi_xbar_stall_sva.sv` 的保序跟踪表用**单 bit** `w_id_open[id]`
表示"该完整 ID 有事务在飞"。spec §5.2.4 明确允许同 ID、同方向、**同目标
master 端口**的多笔事务合法堆积——此时两笔共用同一个 bit：

```
第 1 笔 AW 接受 → w_id_open[id] = 1
第 2 笔 AW 接受 → w_id_open[id] = 1   （同一个 bit，无法区分两笔）
第 1 笔 B 返回  → w_id_open[id] = 0   ← 第 2 笔仍在飞，记录却被清掉
```

自此第 2 笔从跟踪表中消失，针对它的乱序检查静默失效。读侧 `r_id_open`
同构。

方向是**漏检（假绿侧）**——不会造成假红，只会让本该被检出的乱序悄然通过。

## taxonomy

TB_BUG

## rca

1. 跟踪表以「完整 ID → 1 bit 在飞标志 + 目标寄存器 + 序号」建模，隐含
   "每个完整 ID 同时至多一笔在飞"的假设。
2. 该假设与 spec §5.2.4 冲突：同 ID 同方向**同目标**事务不受 §5.2 stall
   约束，可合法堆积（这正是 M2-OR02(a) 与 M2-TL02 构造的情形）。
3. 第二笔接受时只是把已经为 1 的 bit 再写成 1，无新增信息；第一笔完成时
   无条件清 0。
4. 于是"还有几笔在飞"的信息从未被保存 ⇒ 第二笔起的所有事务不在候选集内，
   `w_id_open[cand]` 对它们恒为 0，乱序检查跳过。

与 BUG-0023 的关系：BUG-0023 是**同沿**写冲突（一笔进一笔出撞在同一拍），
已修；本条是**跨沿**的容量不足（两笔同时在飞而只有一个槽位）。两者都源自
同一处数据结构，但成因与修法不同，故独立立项。

## fix

未派发。修复方向（不预设实现）：让跟踪表能表达"同一完整 ID 有 N 笔在飞"，
且 §5.2.1 的候选判据（异目标、更老、仍在飞）在 N>1 时仍然成立。注意与
BUG-0023 已落地的同沿互斥保护协同——两者改的是同一组 `always_ff` 赋值。

严重度中：只影响漏检，不影响已登记证据的有效性（见下），但它使
`stall_sva` 的乱序判决在 §5.2.4 允许的堆积场景下**名存实亡**，而 M2-TL02
恰恰就是这种场景。

## 对已登记证据的影响

**无影响**：本条只会漏检、不会误判。七条 M2 证据均为零失配/零断言失败，
没有任何一条 PASS 依赖该跟踪表在多笔堆积下的正确性——它们的判决锚点是
scoreboard 的完成序判据（独立于本 SVA 模块）。

但反向要注意：**M2-TL02 的 SVA 侧保序检查在本条修复前是空转的**（该场景
全程同一完整 ID 堆积 ⇒ 第二笔起都不在跟踪表内）。该场景的判决门锚在
scoreboard 正确性 + 达标 cover（见 testplan M2-TL02 行），不依赖此 SVA，
故结论不变；但"SVA 也过了"这句话对 TL02 不构成独立证据。
