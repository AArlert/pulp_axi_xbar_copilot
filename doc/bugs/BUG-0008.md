# BUG-0008 — M0 期三条证据记录的 `## Key check lines` 段为空

## symptom

`doc/evidence/v0.0.1/{M0-01,BUG-0001,BUG-0006}.log` 三条已登记证据的
`## Key check lines` 段一行没有。三条证据的判决本身是稳健的（两腿制
fail-closed：`Summary: 3198 assertions, 1924 with attempts, 0 with failures`
在档，UVM/VCS 腿亦过），但摘要没有如实反映功能记分板的结论——要确认
"Tests Failed: 0"，读者必须回到 `sim/out/` 的源日志重读。

对照组：0.2.1 之后登记的 `v0.1.0/M1-01.log`、`v0.1.1/BUG-0007.log` 两条
该段各有 2 行，不受影响。

## first_anomaly

signoff-M0 人工抽检第 4 项（R1）首次发现并回流框架，记为
`doc/fw-feedback.md` FB-6。当时判断为"证据摘要保真缺口，判定不受影响"，
里程碑照常签核放行。

## taxonomy

TOOL_ENV

工具产物保真缺口，非 DUT/TB/spec 问题。命中 taxonomy 表里
"evidence older than the code it certifies" 同一档：证据文件本身没错，
但它是由有缺陷的抽取器生成的，下一个读它的人会被误导。

## rca

框架 `scripts/evidence.py`（≤0.2.0）两处窄化，对非 UVM tb 同时失效：

1. 纯 VCS 分支的摘要窗口只取完成横幅上方 2 行
   （`lines[max(0, idx - 2):idx + 8]`）。上游 `tb_axi_xbar` 由 ucli
   `run; exit` 驱动 `$stop`，其记分板判决行落在横幅上方 4~7 行处
   （实测 `sim/out/upstream_sanity_1.log`：`Simulation has ended!` 距 7 行、
   `Tests Failed: 0` 距 4 行），全部在窗口之外。
2. `KEY_LINE_RE` 只认 UVM 形状的 `pass|match|compare ok|check ok|running
   test`，而上述判决行一个都不匹配。

两者叠加 → 该段必然为空。M0 三条证据全部来自这一 tb 形状，故全中；M1 起
改用自建 UVM env，故不再复现。

## fix

框架侧修复，非本仓库改动（`scripts/` 禁止本地修改）：iverif-workflow
0.2.1 把窗口放宽到 20 行、`KEY_LINE_RE` 增补
`tests failed|ended|mismatch`，并附保险丝测试
`test_plain_nonuvm_verdict_line_captured`。本仓库已 `fwsync --pull`
至 0.3.0（`make fw-check` 绿）。

## rerun

**存量三条不追溯重写。** 理由：`doc/evidence/v0.0.1/` 是 signoff-M0
已签核指向的产物，用新抽取器重新生成会改写被签核对象的字节，而签核记录
本身无法同步重签；相比"摘要不全"，"签核指向的证据在签核后被改过"是更重
的可追溯性损伤。源日志 `sim/out/upstream_sanity_1.log` 仍在，任何人可自
行复核。

若 rev 认为应当重生成，路径是：重跑 `make evidence` 覆盖三条 → 在
signoff-M0 追加一条重签说明 → 本记录转 CLOSED 并填 verify_evidence。
**该裁决属 rev，orch 不自行 WONTFIX。**

## regression_guard

框架侧已有（保险丝测试，见 fix）。本仓库侧的守卫是抽检习惯本身：
里程碑签核的人工抽检项须实际打开证据文件确认关键行段非空——R1 正是这样
抓到的，这条经验值得保留而不是依赖工具永不再犯。
