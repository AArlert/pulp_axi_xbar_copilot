# BUG-0027 — scoreboard 保序判据把同一完整 ID 的完成响应归属到**最新**那笔，§5.2.4 合法堆积被误判为乱序（假红）

## symptom

`tb/scoreboard_refmodel.sv` C5.1/C5.3 的 §5.2.3 完成序判据在完成时刻要先
"认领"这笔 B/rlast 对应哪条 open 记录。原实现遍历 `or_open_q[k]` 且
**不 break**，于是 `this_idx` 停在**最后一条**同完整 ID 的匹配记录上：

```systemverilog
foreach (or_open_q[k][idx])
  if (or_open_q[k][idx].slv_id == ro.id) begin
    this_idx = idx; this_found = 1'b1;   // 无 break ⇒ 取最新一条
  end
```

M2-OR03 的构造（单一完整 ID `X`：先 n_a 笔目标 A 合法堆积，再 n_b 笔同 ID
目标 B）里，队列同时存在 `[X→A ×14, X→B ×4]`。第一笔 X→A 的 rlast 完成时，
判据把它认领成**最新那条 X→B 记录**，再与"更老、仍在飞、异目标"的 X→A 记录
比较 ⇒ 报乱序：

```
UVM_ERROR ../tb/scoreboard_refmodel.sv(647) [SB_OR_REORDER] slv port 5
id-bucket 'h5 dir=R: id 'h5 (accepted @685000, mst 6) completed ahead of
older still-open id 'h5 (accepted @545000, mst 5) — spec §5.2.1/§5.2.3
response reordering
```

同一次运行 **336 条**该报错，而同一份运行里 route 864/864、resp（读数据逐
beat 预测比对）864/864、resp-route 864/864 全 match，SVA 2143 条断言 0 失败
⇒ DUT 侧转发序与完成序均正确，报错是 checker 的归属逻辑造成的**假红**。

方向是**假红**（与 BUG-0023/0024 的漏检方向相反）。

（本仓库不产 FSDB，BUG-0020）。

## rca

1. §5.2.3 判据需要先确定"这笔完成属于哪条 open 记录"，同一 bucket 内此前
   只出现过**不同完整 ID**的记录（M2-OR01/OR02 每对用两个不同完整 ID），
   匹配唯一，取第一条还是最后一条没有区别。
2. M2-TL02 起出现同一完整 ID 多笔在飞，但全部**同目标**，两种取法得到的
   `mst_port` 相同 ⇒ 差异仍不可见。
3. M2-OR03 第一次把"同一完整 ID × 多笔在飞 × 异目标"三者凑齐：取最后一条
   ⇒ 认领到 X→B，而 X→A 更老且异目标 ⇒ 判据必然翻红，且对**每一笔** X→A
   的完成都翻一次。
4. 正确取法是**最早一条**：同完整 ID 同方向的响应按接受序返回（AXI 同 ID
   保序，spec §1/§5.2.3），队列按接受序 push，故第一条匹配即该笔。
5. 同族对照：`tb/slvport_agent.sv` 的 R burst 配对早已写明"First match =
   oldest same-ID record, which preserves the same-ID in-order property
   (spec §5.2)"——同一规则在 monitor 侧落地、在 scoreboard 侧漏掉。

## fix

commit: <待 orch 回填>
what: `tb/scoreboard_refmodel.sv` 完成时刻的记录认领改为**最早匹配**
（`foreach` 内 `break`），并注明：同一完整 ID **内部**的先后本判据不判
（B 只带 id+resp，边界上无法区分两笔同 ID 写），该向由 master 侧 FIFO
路由判据（`SB_ROUTE`——转发序一旦交换即翻红）与读侧逐 beat 数据判据
（`SB_RDATA`——数据把响应钉回具体那笔）承担。

**不放宽任何既有判决**：跨**不同**完整 ID 的 §5.2.3 乱序检测（M2-OR01 的
判据本体）完全不变（那里匹配唯一）；改动只影响同完整 ID 多笔在飞时的认领，
而那种情形下旧写法是**恒假红**（合法与真乱序都翻红），不携带判别信息。
