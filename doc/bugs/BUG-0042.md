# BUG-0042 — AW/W pairing FIFOs (mstport_agent monitor+responder,
axi_chan_sva WLAST) assumed AW never arrives at a master port later than
its own W burst — false under `FallThrough=1'b1`

## symptom

M4-FT01 (`cfgE`, `FallThrough=1'b1`, baseline `LatencyMode=CUT_ALL_AX`
otherwise unchanged) card: `make run TEST=m4_ft01_cfge_test SEED=1`
initially produced, in order as the fix landed:

1. `mstport_agent.sv` monitor: `UVM_ERROR [MON_WNOAW] mst monitor saw a W
   beat with no accepted AW queued` (6 hits, one per master port) followed
   by `UVM_ERROR [SB_NOPEND] mst port N observed id 'h0 with no matching
   pending record`, then `UVM_FATAL [WATCHDOG] tb_top watchdog: simulation
   exceeded 200000ns without natural completion` (sim never reaches
   `$finish`).
2. After fixing (1) alone: no more `UVM_ERROR`, but the watchdog STILL
   fired — every one of the 6 slave ports' very first (ordinary, non-probe)
   write hung forever in `slvport_driver::drive_write()`'s completion wait
   (`wait (got_b && got_r)`), because `mstport_responder`'s own
   `w_collect_loop()` has the identical FIFO-empty assumption and, on an
   empty `aw_pending_q`, silently reused a **stale/default `cur`** (task-
   local, uninitialized `id=0` on this port's first-ever write) to generate
   the B response — so a B for id 0 arrived while the driver waited on the
   item's REAL id, forever.
3. After fixing (1)+(2): no more errors from those two components, but 16
   `UVM_ERROR [SVA_WLAST_LEN] WLAST beat index N != AxLEN M` from
   `tb/sva/axi_chan_sva.sv`, **all at `gen_mst_sva[*]` (master-port
   instances only, never a slave-port instance)** — the same FIFO-empty-
   at-w_last assumption, this time in the protocol SVA's own AW-len/W-beat-
   count pairing.

## first_anomaly

signal: `mst_if[5].aw_valid` / `mst_if[5].w_valid` (master port 5, an
ordinary `slvport_basic_seq` hit write — not even one of the card's
`fallthrough_probe` items)
time: 135000ps (a `w_valid&&w_ready` beat with `aw_valid==0`) vs. 145000ps
(that same write's `aw_valid&&aw_ready` — one full 10ns cycle LATER)
how_found: a temporary per-cycle `$display` of
`aw_valid/aw_ready/w_valid/w_ready/w_last` at `mstport_agent.sv`'s monitor
(removed before delivery, per-cycle trace only used for this RCA — no
DUT-internal signal read, only the already-externally-observable
`mstport_if` fields every monitor/SVA in this file already reads) showed,
for master port 5's very first accepted write:
```
t=135000 awv=0 awr=1 wv=1 wr=1 wlast=0
t=145000 awv=1 awr=1 wv=1 wr=1 wlast=0
t=155000 awv=0 awr=1 wv=1 wr=1 wlast=1
```
i.e. this write's W beats started (and were being accepted) a full cycle
BEFORE its own AW appeared at this master port.

## rca

```
observed:   mstport_agent monitor+responder + axi_chan_sva all assumed "AW
            accepted no later than its own W burst" at a MASTER port
anomaly:    at mst port 5, `w_valid&&w_ready` fires with `aw_valid==0` one
            cycle before that same write's AW handshake
chain:      Cfg.FallThrough=1'b1 (spec §2.1: AW routing decision "falls
            through" combinationally onto W) + baseline LatencyMode=
            CUT_ALL_AX (`MuxAw` spill register present on the master-port
            side, `MuxW` absent — spec §7.2 bit map) → an already-decided
            write's W beat can reach the master port's un-spilled W path
            the same cycle it becomes ready, while that write's own AW is
            still draining through the one-cycle `MuxAw` spill → W beat
            observably precedes its own AW at the external master port
            → the shared AW/W-len FIFO pairing logic in three components
            (mstport_agent's monitor AND responder, axi_chan_sva's WLAST
            check) all assumed the opposite order and either raised a
            false error, silently mispaired with stale/wrong data, or
            (responder) generated a wrongly-ID'd B response the driver
            then waited on forever
```

Nothing here is a DUT/spec finding: AXI4 does not require any relative
order between the AW and W channels (independent channels), and
`doc/spec.md` §5.5.1/§5.5.2 only constrain the *relative* order of
different W bursts to match their AWs' *acceptance* order — never that a
burst's own AW must arrive no later than its own W. The three affected
components' code silently assumed the stronger (unwritten, never-spec'd)
property; every M0-M3 scenario's traffic happened to satisfy it by
construction (sequential `drive_write()` + `FallThrough=0`'s baseline
default kept AW always safely ahead), so the gap was never exercised
before M4-FT01 was the first scenario to set `FallThrough=1'b1`.

## fix

commit: (pending — this card's `tb/mstport_agent.sv` +
`tb/sva/axi_chan_sva.sv` changes land in the same commit as the rest of
M4-FT01; orch fills the sha at closeout)
what: generalized all three FIFO-pairing sites from "AW always precedes
its W" to a symmetric two-queue design — whichever side (AW-accept event,
or W-burst-completion event) arrives first is parked (in `w_actual_q` /
`orphan_w_q` / `orphan_pending_cnt` respectively), consumed by the other
side whenever it eventually shows up, still strict FIFO order on each
side (spec §5.5.1/§5.5.2's guarantee). No published/checked VALUE changed
— only WHEN the pairing/check happens. `mstport_agent.sv`'s
`mstport_responder` additionally had to promote `w_busy`/`cur` from
`w_collect_loop()`-task-local to class-level (via a `w_busy_get()`
accessor) so the concurrently-forked `accept_loop()` can resolve an
in-progress collection; verified (by hand, both possible relative
execution orders of the two forked processes on a coincident edge) that
the result is identical either way — no new race introduced.

## rerun

- `make run TEST=m4_ft01_cfge_test SEED=1` → 0 `UVM_ERROR`/`UVM_FATAL`,
  natural `$finish` at 2365000ps (was: watchdog timeout / UVM_ERROR before
  the fix). `doc/evidence/v0.4.6/M4-FT01.log`.
- Full regression (`make regress`, all pre-existing scenarios, none of
  which set `FallThrough=1'b1`): confirms the widened FIFO logic is a
  strict superset of the old behaviour (empty side-queues ⇒ identical to
  before) and does not change any other scenario's pass/fail.
