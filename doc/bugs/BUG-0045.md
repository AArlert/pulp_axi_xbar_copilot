# BUG-0045 — spec §3.2 未载 `addr_decode_dync` 的 `end_addr == '0` 末端哨兵分支

## symptom

无仿真失败触发——这是一条静态阅读发现的 spec-completeness 缺口，不是某次
运行报的红。`vendor/common_cells/src/addr_decode_dync.sv:112` 的组合匹配
条件是 `(addr_i < end_addr) || (end_addr == '0)`，头注释 L60 明确写
"if `end_addr == '0` end of address space is assumed"——即该模块把
`end_addr=='0` 当作"本条 rule 的地址区间一直延伸到地址空间末端"的哨兵值，
是 RTL 自身文档化的受支持行为。`doc/spec.md` §3.2（L117-119）对地址匹配的
描述只有半开区间 `addr>=start && addr<end` 与 `start<=end` 两条，**未提**
这个哨兵分支。`tb/xbar_types_pkg.sv` 参考模型 `decode_mst_port`
（L336-358，命中判据在 L354）同样只实现了半开区间比较，未实现哨兵分支。

## fix

> **2026-08-03 终结（SPEC_CHANGED）——先读本段，下方为历史记录。**
> `doc/spec.md` §3.2 新增 clause 3（终址哨兵 `end_addr == '0` ⇒ 等效终址
> `2^AxiAddrWidth`，非零长度区间；标注"来源：RTL——上游文档未载"）与 clause 4
> （实现侧区间非空约束 + DV 地址表环境约束），与 **BUG-0046 合并解决**，
> spec Change record #13，已重 pin。
>
> **为何与 BUG-0046 合并**：`check_start`（`start_addr < end_addr ||
> end_addr == '0`）把哨兵解码后等价于**单一**严格判据
> `start_addr < effective_end`（`start_addr` 为 `AxiAddrWidth` 位，恒
> `< 2^AxiAddrWidth`，故 `|| end_addr=='0` 不是"豁免分支"，而是同一条严格 `<`
> 在哨兵编码下的写法）。BUG-0046 所称"RTL 禁止 `start==end`"**必须**以本条的
> 哨兵为前提才能准确陈述——`start==end=='0` 合法（覆盖全地址空间），
> `start==end!='0` 才非法。两条不是"同源的两条独立缺口"，而是同一条区间契约的
> 主干与其编码约定，一条 clause 对不可分。
>
> **REV-021 的反对被部分尊重**：其"补 spec+refmodel 会造不可证伪死代码"的顾虑
> 在 **refmodel 半边成立**——`tb/xbar_types_pkg.sv` 的 `decode_mst_port` 哨兵
> 分支**本次不实现**，留待 M5 真构造该类地址表时与定向场景同批落地（见
> `doc/guards.md` G-0045）。在 **spec 半边不适用**：本项目本就容忍 spec 条款跑在
> 场景前面（`make check` 长期报 `spec subsections cited by no scenario`，是机器
> 已跟踪的信息性缺口，非违规）。
>
> **流程偏离留痕**：用户明确指示 orch 直接标注、不派 arch/rev 卡（CLAUDE.md §0
> 常规要求 spec 改动走 arch 起草 → rev 门禁 → orch 应用）。见 `doc/log.md`
> [0.5.3] 区块。

以下为终结前的原记录（历史）：无 RTL/TB/spec 改动（现阶段）——**REV-021 终判：taxonomy 维持 SPEC_ISSUE（潜伏型 spec-completeness
gap，命中"完全未定义"支）；处置 = ACCEPTED@M5。** rev 独立核实（算术
自验 8 条 rule 的 `end_addr∈{0x1000_0000..0x8000_0000}` 不回绕到 0 +
tb 全域 `end_addr`/`ADDR_MAP` 构造点扫描）确认"当前无任何场景构造
`end_addr=='0` 的地址表"为真——分歧是**潜在**（一旦有场景触及即刻现形），
**非当前存在**（DUT 与 refmodel 对每个实际出现的地址判决一致）。这一
"潜伏 vs 当前"区分决定了处置排除以下两条：
- **排除"现在补 spec §3.2 + refmodel 同步实现"**：deferred ledger
  （trigger 未 fire）+ 现在补会造出无场景激励的 refmodel 死代码，永不
  可证伪（`workflow/review.md` Q2"a checker that cannot fail is
  decoration"）。正确时序是 spec 条款 + directed 场景 + refmodel 分支
  三者同批落地。
- **排除 WONTFIX**：`end_addr=='0` 哨兵在 RTL 匹配（L112）、`check_start`
  合法性断言（L148）、`check_overlap` 重叠断言（L157）三处均有专设支持，
  是模块文档化、断言背书的受支持特性，WONTFIX 会永久埋没它；且
  `workflow/bugs.md` 状态语义"WONTFIX may not mean 'later'"——本条应在
  M5（验证方法学拓展里程碑）复访，即"later"，WONTFIX 是误标。

**可证伪的解锁条件**：一旦任何场景（含 M5 新增场景）构造 `end_addr=='0`
的 rule，本 ACCEPTED 立即作废，必须先走 SPEC_ISSUE 标准处置（arch 起草
§3.2 补充条款 → rev 仲裁 → 重 pin → refmodel 同批实现哨兵分支），绝不
允许 DV 现场在 checker/refmodel 里发明该情形下的期望目标端口。**M5 到期
动作**：M5 签核 rev 二选一——(i) 决定覆盖哨兵，走标准处置三件套；
(ii) 出具"本项目受验配置空间内不使用哨兵"的具体论证后改 WONTFIX。哨兵
条款草案已由 REV-021 §3 预置备料（现在不落 spec，供 M5 解锁时照抄）。

详见 `doc/review/REV-021.md`。
