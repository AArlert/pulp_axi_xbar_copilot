# BUG-0041 — `addr_decode_dync` end-of-sim debug assertion fires on spec-legal rule overlap (SPEC-3.1.3)

## symptom

M4-OV01's first draft (address table with one pair of legally overlapping
rules, SPEC-3.1.3) produced 12 `[ASSERT FAILED]` lines — one per
(slave port × AW/AR) instance of `addr_decode_dync` in the DUT's
instantiation closure — even though the run's functional judgement was
clean: `UVM_ERROR : 0`, `UVM_FATAL : 0`, and the scoreboard reported
`route: match=48 mismatch=0` (the DUT's actual routing decisions already
followed SPEC-3.1.3's "higher table position wins" tie-break correctly).
`scripts/svacheck.py` treats these lines as a hard FAIL (Layer 1 —
`"file", line: hier: started at ... failed at ...` — and Layer 1b both
match), so an unmodified M4-OV01 would never have produced an evidence-
eligible log despite the DUT's functional output being correct.

`"...addr_decode_dync.sv", 133: ...: started at 945000ps failed at
945000ps` engine lines. `python3 scripts/svacheck.py <that log>` confirmed
verdict FAIL (Layer 1 hit, 12 occurrences).

## fix

**No RTL/spec change — DV applied a stimulus-side workaround scoped to
M4-OV01 itself, already part of this card's delivered code; the
underlying vendor-RTL characteristic (a debug-only end-of-sim assertion
whose implicit onehot0 assumption is inconsistent with the module's own
documented overlap-support feature) remains un-triaged and is registered
here for rev disposition (WONTFIX / accepted-vendor-quirk vs. an upstream
report), not "fixed" in the DUT_BUG sense.**

what: `tb/seq_lib.sv`'s `slvport_ov01_seq::body()` now appends one closing
write/read pair per slave port, deliberately routed to region 1 (untouched
by `ADDR_MAP_OV1` — only `OV1_LOW_RULE`/`OV1_HIGH_RULE` were remapped), so
every port's AW/AR address bus is left holding a non-overlapping address
once the vseq completes, keeping `matched_rules` onehot0 at `$finish`. This
does not touch RTL, does not disable the assertion project-wide (which
would have required a compile-time `+define+COMMON_CELLS_ASSERTS_OFF` or
the module's own `+disable_assert_final_checks` plusarg — either would
silence the check for every *future* test, a strictly wider change than
this card's scope warrants, and neither was applied), and does not weaken
what M4-OV01 judges — SPEC-3.1.3's tie-break is already fully exercised by
the `num_iter` overlap-region legs that precede the closing pair. Rerun
after the fix: `make run TEST=m4_ov01_overlap_test SEED=1` → 0
`[ASSERT FAILED]` lines, `python3 scripts/svacheck.py <log>` → CLEAN,
`SB_SUMMARY route: match=60 mismatch=0`.

commit: (this card's tb/ changes — see delivery report; no separate fix
commit, the workaround ships together with the M4-OV01 scenario)

## regression_guard

type: directed_test + checklist
paths: tb/seq_lib.sv, tb/xbar_types_pkg.sv
ref: `tb/seq_lib.sv` `slvport_ov01_seq::body()`'s closing pair (region-1,
non-overlapping) + `tb/xbar_types_pkg.sv` `ADDR_MAP_OV1`/`OV1_LOW_RULE`/
`OV1_HIGH_RULE`.
note: any future scenario that drives `addr_map_i` overlap (SPEC-3.1.3)
must either (a) end every slave port's own AW/AR traffic on a
non-overlapping address before the test's `$finish` (this card's pattern),
or (b) explicitly pass `+disable_assert_final_checks` with a written
rationale in its own testplan row/vseq header — otherwise
`scripts/svacheck.py` (Layer 1/1b) will legitimately FAIL the log even
when the scoreboard's own route/data/response judgement is clean. This is
a checklist item until/unless rev's triage of this bug produces a
mechanized guard (e.g. a lint rule flagging address-table overlap
construction sites that don't end on a disjoint address).
