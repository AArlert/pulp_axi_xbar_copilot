## 3. Taxonomy 终判：**SPEC_ISSUE**（改判 DUT_BUG）

**成本阶梯 `TOOL_ENV → TB_BUG/CONSTRAINT_BUG → SPEC_ISSUE → DUT_BUG` 逐级排除：**

- **TOOL_ENV — 排除**：现象在 orch 两次独立重跑 + 已提交日志中**确定性**复现，与
  seed/机器无关，无编译期异常；根因是 RTL 结构而非工具。
- **TB_BUG / CONSTRAINT_BUG — 排除**：激励合法（单 slave→单 master 同桶/同 ID 连发
  不违反 AXI 保序，spec §5.2.4；桶跨 4 兄弟 ID、每 ID ≤3 远低于任何 per-ID 门，不触发
  假冲突 stall）；directed test 无随机约束；checker 期望忠实 spec、计数经 scoreboard
  全绿（144/96 笔正确配对）与 `SVA_TXLIMIT reached` 非空转佐证。非 TB 侧缺陷。
- **SPEC_ISSUE — 命中，且 DUT_BUG 未被清空**：见下。

**为何是 SPEC_ISSUE 而非 DUT_BUG（举证：清空一切之后仍未归咎 DUT，因为 DUT 有
完全站得住的另一读法）：**

1. **参数从不进比较器，只进 `idx_width` 定宽（§1 a-f）。** 若"恰好 MaxTrans"是硬
   契约，标准写法是 `in_flight == MaxTrans` 门；RTL 中**不存在**任何 MaxTrans 值比较。
   full 判据是 `&in_flight`（计数器满量程）——这是**位宽契约**，不是值契约。`MaxTrans`
   在结构上是"把计数器定得至少能表示这么多"的**定宽提示**。

2. **有效上限对多数取值都不等于 MaxTrans，且可低于 MaxTrans（§1 b）。** 有效封顶
   `= 2^⌈log₂(MaxTrans)⌉ − 1`：MaxTrans=10 ⇒ 15（>10）；**MaxTrans=8 ⇒ 7（<8）**、
   MaxTrans=16 ⇒ 15（<16）。即便对 2 的幂这类常见取值，"up to and including MaxTrans"
   （demux.md L72）也在**限制方向**被违反。仅当 `MaxTrans = 2ᵏ−1` 才恰好相等。一个若被
   当作硬上限就会在 MaxTrans=8 这种自然取值上"少一笔"的量、多年未被上游作为 bug 修正
   （CHANGELOG 仅修过 MaxTrans=1 位宽退化，未修过一般越限），只可能因为社区把 MaxTrans
   理解为**近似定宽参数**、而非精确上限。

3. **越限零功能/协议损害（§1 l）。** 同批 scoreboard 路由/数据/响应路由/完成/保序
   全绿、UVM_ERROR 0。AXI 协议**不规定**任何在飞事务数上限——超出 MaxTrans 不产生任何
   **错误的 DUT 输出**（每笔仍正确路由、数据正确、正确完成），计数器也未真正 overflow
   回绕。taxonomy 的 DUT_BUG 判据是"**DUT output violating an explicit spec clause**"；
   这里被违反的是一个**资源定宽参数的散文数值**，而非任何可观测协议行为，且**没有
   任何错误输出**。

4. **许可来源自身三方矛盾（§1 k）。** demux.md L72 / xbar.md L46-L47 / axi_pkg
   L489-494 对同一对参数给出三种互不相容的定义（每桶 / 每 slave 端口聚合 & 每 master
   端口 per-ID / 每外接 master·slave 聚合），**无一与 RTL 精确吻合**。这是 SPEC_ISSUE
   的教科书签名——"spec 与上游文档相抵触，或未定义该行为；DUT 与 TB 各自在不同读法
   下都站得住"（taxonomy SPEC_ISSUE 判据）。DUT 的读法（MaxTrans=定宽提示，封顶
   满量程）完全站得住；TB 的读法（≤MaxTrans 硬上限，取自散文）也站得住——正是
   SPEC_ISSUE。

5. **MaxSlvTrans 侧更甚：文档描述的机制在 RTL 中根本不存在（§1 i-j）。** `MaxSlvTrans`
   经 xbar.sv L141 连到 mux 的 `MaxWTrans`——AW→W 的 ID 高位 FIFO 深度（mux.md L29），
   **不是**"每 master 端口每 ID 在飞上限"（xbar.md L47）。mux 无 per-ID 在飞计数器。
   故 master 端口每 ID 在飞受**上游 demux 每桶有效上限**（第 2 点，15）主导、可超
   MaxSlvTrans（见证达 8>6）。这**证伪** REV-005 为 M2-TL02 解锁的"每端口×每 ID×每
   方向 ≤ MaxSlvTrans、绝不假红"可观测上界监视器——该监视器**会**假红，其前提（mux
   存在 per-ID 上界机制）不成立。此侧连"DUT 违反上限"都谈不上：被引的上限机制不存在。

**结论**：DUT 未产生任何错误输出，且对 `MaxTrans` 语义持一个由 RTL 结构完全支撑的
另一读法（定宽参数），而许可来源自身三方矛盾。据 `discipline.md` rule 1，不得因"RTL
封顶 15 故 15 即意图"下 DUT_BUG，也不得因"散文写 ≤MaxTrans 故 MaxTrans 即硬契约"反向
臆断——两者都缺正面证据支撑"精确 MaxTrans 硬上限"是上游意图；而结构证据（无值比较器、
2 的幂下反向违反、零功能损害）正面支持"定宽提示"读法。**DUT_BUG 未被挣得**（"earned by
eliminating everything else, not reached by default"——SPEC_ISSUE 这一更便宜的解释非但
未被清空，反而是证据更充分的一个）。**终判：SPEC_ISSUE。**

（本卡三条"请重点排除的替代解释"逐一清账：**#1** 无 MaxTrans 合法性检查（§1 g）⇒
baseline MaxMstTrans=10 是**合法**配置，非"未按规范配置"，裁决不反转为环境侧违规；
**#2** 无任何独立于该计数器、在恰好 10/6 处限流的上层背压——mux 侧只有 MaxWTrans=6 的
AW→W FIFO 深度、无 per-ID 在飞门，demux 每桶门（15）是唯一主导限流点；**#3** `overflow`
是内部计数器最高位、仅在计数达 16 置位（§1 e），被 `&in_flight`=15 提前阻止，**永不在
计数=10 处先行触发**——"全一才 full"结论完整。三条替代解释全部排除。）

## 5. Spec 修订建议（原文 / 新文 / 理由）+ orch 应用范围

> rev 只出裁决实质；**spec 正文精编 + sha256 重 pin + 状态转 SPEC_CHANGED +
> suspect DUT→SPEC 由 orch 应用**（同 REV-005/006 先例，非 rev 落笔）。以下给出
> 精确编辑范围与实质，措辞由 orch 在此范围内 surgical 定稿。

**(1) §5.4.1（MaxMstTrans 有效上限）**
- 原文（要点）："每桶 in-flight 事务数 **≤ `MaxMstTrans`**"。
- 新文（实质）：每桶 in-flight 事务数的**有效上限 = demux 每桶计数器满量程 =
  `2^idx_width(MaxMstTrans) − 1 = 2^⌈log₂(MaxMstTrans)⌉ − 1`**（`IdCounterWidth =
  cf_math_pkg::idx_width(MaxMstTrans)` 位、"full" 判据为计数器全一 `&in_flight`、
  **无 `== MaxMstTrans` 比较**）；基线 `MaxMstTrans=10 ⇒ 有效上限 15`。`MaxMstTrans`
  是**计数器定宽参数**（保证计数器至少能表示该值），**非精确在飞上限**；仅当
  `MaxMstTrans = 2ᵏ−1` 时有效上限恰等于 `MaxMstTrans`（2 的幂等取值下有效上限**低于**
  `MaxMstTrans`，如 MaxTrans=8⇒7）。标注 **（来源：RTL——上游文档 demux.md L72
  "up to and including MaxTrans" 与实现不符；上游文档不精确）**。
- 理由：§3 第 1-4 点。RTL 结构（idx_width 定宽 + `&in_flight` 全一判满、无值比较器）
  证明 MaxTrans 是定宽提示；越限零功能损害；同 BUG-0004/0013 型"RTL 实现细节未被字面
  '上限'蒸馏捕获"。

**(2) §5.4.2（MaxSlvTrans 非在飞上限）+ §2.1 `MaxSlvTrans` 字段行**
- 原文（要点）："每 master 端口每（前缀后完整）ID in-flight ≤ `MaxSlvTrans`"。
- 新文（实质）：**撤销**"≤ MaxSlvTrans"作为每 ID 在飞可断言上界。`MaxSlvTrans` 经
  `axi_xbar.sv` L141 映射到 `axi_mux` 的 `MaxWTrans`（mux.md L29：AW→W 之间保存 ID
  高位的 **FIFO 深度**），**不是**每 ID 在飞事务上限；mux 侧**无**按 ID 分桶的在飞
  计数机制（复核 BUG-0011）。故 master 端口每 ID 在飞数由**上游 demux 每桶有效上限
  （§5.4.1）主导，可超 `MaxSlvTrans`**（基线见证达 8>6）。标注 **（来源：RTL——上游
  文档 xbar.md L47 "per ID in flight" 与实现不符）**。
- 理由：§3 第 5 点。xbar.sv L141 参数连线 + mux.md L29 语义 + mux 无 per-ID 计数器 +
  仿真见证 8>6 且 SB 全绿。此条同时**正式收回 REV-005 为 BUG-0011 解锁的"≤6 绝不
  假红"可观测上界监视器**——该监视器前提不成立、会假红，**不得升格为 assert**。

**(3) §5.4.3 与 §7.4.5（收口"上限最终被守"）**
- §5.4.3 原文"`MaxMstTrans` 侧机制明确——同桶计数达上限即拒收"：改为"达**有效上限**
