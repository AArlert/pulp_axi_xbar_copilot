## 裁决摘要（先给结论，不和稀泥）

**DUT_BUG 不成立。** BUG-0034 的正确 taxonomy 是 **TB_BUG**（checker/monitor
在**合法的**跨 ID R 交织下误报）。**不发起上游 issue**——DUT 行为与其自身
上游文档一致，二者并无矛盾，报上游属误报。

诊断卡的**机械工作可信**（三工具证据、RTL 行号、物理逐拍序 id0,id0,id8,id0,id0
均经我独立复核为真、行号全部准确）；但其**协议解读与 taxonomy 归因错误**，错在
三处，任何一处都足以否掉 DUT_BUG 定性：

1. **spec 援引是伪造的。** 诊断卡称"spec §5.5.3——slave 端口 R burst 不得与他源
   交织"。实读 §5.5.3（doc/spec.md L311-312）原文是"slave 端口上，来自不同 master
   端口的 B/R 响应经 **round-robin 仲裁合并**（demux.md §Design Overview）"——它
   **描述**了正被观测到的交织，而**不禁止**它。禁止交织的条款只存在于 **§5.5.1（W
   通道）**，R 侧**没有**对应条款。更进一步，**§5.5.4（C4，REV-001 §3.2）明文禁止
   checker 断言"任何一条特定 round-robin 发生序、某一拍的具体被授权端口"**——诊断卡
   命中的三个 checker 恰恰断言的就是这个。
2. **TB_BUG 假说是被"范畴错误"否掉的。** 诊断卡以"两个独立 FSDB 解析器逐拍一致"
   宣称否证 TB_BUG。但两个解析器证明的是**物理 beat 顺序为真**，**不**证明"该顺序
   构成协议违反"，也**不**证明"scoreboard 的截短/悬挂判决正确"。这正是本卡任务提示
   点名的陷阱：观测一致 ≠ 观测解读正确。
3. **四路症状全是 TB 重建产物，可逐条闭合解释。** 见下 Item 3。

## 逐项裁决

### Item 1 — RTL/结构复核：诊断卡的机械分析成立（pass）

我逐行复核了诊断卡引用的 RTL，**行号与结构结论全部准确**：

- `i_r_mux` = `rr_arb_tree #(.LockIn(1'b1))`，例化起于 axi_demux_simple.sv L383
  （`) i_r_mux` 在 L388）。✓
- `i_ar_id_counter` 起于 L355，atop 读经 `inject_i`（L367）注入、`inject_axi_id_i`
  = `aw.id` 低位（L366）。✓
- rr_arb_tree.sv L151 `lock_d = req_o & ~gnt_i`；L167 断言明文"仅在 output 未
  ready（stall）时锁 idx"。✓
- **结构结论成立**：LockIn 只在**握手 stall**（`req_o & ~gnt_i`）时锁存 idx，
  全文不引用 `r.last`/burst 概念；R 通道**无 burst 级仲裁锁**。本 TB `r_ready`
  恒 1（slvport_agent.sv:45）⇒ 每拍 `gnt_i=1` ⇒ `lock_d≡0` ⇒ 仲裁器**每拍自由
  重裁**、允许 grant 在 burst 中途逐拍切换 master 端口。

我另行确认了诊断卡**未**点破的一个机制细节（对定性有用）：`i_ar_id_counter` 的
目标绑定寄存器 `mst_select_q` **只随 `push_en` 加载**（L618），而 atop 走的是
`inject_en`（L555）——**注入只 +1 占用计数、从不写目标寄存器**。故 atop 影子读
**结构上不参与** §5.2.1 的"跨端口 select 匹配 stall"。这解释了两笔同桶、异目标
的读为何能并发在飞。**但这不改变定性**（见 Item 2）。

裁决：诊断卡对 RTL 与物理逐拍序的观测**为真**，予以采信。

### Item 2 — 交织的合法性：许可来源穷尽，R 跨 ID 交织被**明文允许**（issue：诊断卡定性错误）

我穷尽了全部许可来源（spec 钉定本 + 上游三份 doc），就"R 数据交织是否被禁止"
得到**唯一且一致**的结论——**不禁止，且被明文允许**：

- **上游 doc 中唯一的"交织禁止"只针对 W**：axi_xbar.md L105"AXI does not allow
  interleaving of **W beats**"；axi_demux.md L14"beats from different **W bursts**
  may not be interleaved"。全库 `grep -i interleav` 命中四处，**无一处禁止 R/响应
  交织**。
- **上游 doc 把"交织不同 ID 的响应"当作性能特性**：axi_mux.md L18——扩展 ID 使
  各 master 拥有互不相交 ID 空间，"leading to potential performance increases...
  **as this could enable a slave module to interleave the responses**"。
- **钉定 spec 忠实蒸馏了这一非对称**：§5.5.1 载 W 不交织；§5.1.4（L190-191）
  明文"（mux.md）...**允许 slave 模块交织不同 ID 的响应**"；§5.5.3 载 R round-robin
  合并；§5.5.4 明文**禁止 checker 断言任何 beat 级发生序**。

本场景两笔读的**完整 ID 为 0x00 与 0x08，互不相同**（低 3 位桶相同不等于同 ID；
§5.2.3 的保序只约束**完整 ID 相同**者）。因此观测到的"id0 与 id8 逐拍交织"是
**不同完整 ID 之间的响应交织**——**恰是 §5.1.4 / §5.5.3 明文允许、§5.5.4 禁止
断言的那类行为**。

**裁决：许可来源已穷尽，未见任何禁止 R 跨 ID 交织的条款；相反见到明文允许
（§5.1.4、mux.md L18）。** 诊断卡援引的"§1/§5.5.3 禁止读交织"在钉定 spec 中
**不存在**，属把"§1 完整 AXI4"外推成一条 spec 未载的硬约束——这正是 taxonomy
"期望值不得来自 RTL/凭空"红线要防的反面（此处是凭空造条款，不是抄 RTL，但同样
无许可来源支撑）。

### Item 3 — 四路症状可逐条闭合为 TB 重建产物（issue：症状不指向 DUT）

我亲读了两个检测点，确认它们**共享同一条"R 永不交织"的重建假设**，在合法交织下
必然误报。以诊断卡自己的逐拍表（165/175 id0，185 id8-last，195/205 id0）代入：

**slvport_agent.sv L503-548（UVM monitor）**：其注释宣称按 r_id 配对 atop R 与
普通读 R——但只在 **burst 起始**（`!r_busy`）配对，一旦 `r_busy=1` 便**盲收所有
后续 beat 直到 r_last，不再校验逐拍 r_id**（L530-533 无 r_id 判等）。代入：
- 165 id0：!r_busy→按 id 匹配到 id0 记录、删除该记录、r_busy=1。
- 185 id8(last)：r_busy=1→**把 id8 的 beat 压进 id0 的 burst**，r_last=1→按 r_cur(id0)
  收口，**id0 得 3 拍** ⇒ `SB_RBEATS beat count 3 != 4`；id8 的 atop R 记录从未被
  取用 ⇒ `SB_ATOP_DANGLING`（B seen R not）。
- 195 id0：!r_busy→找 id0 记录，但已于 165 删除 ⇒ 无匹配 ⇒ `MON_RNOAR`。

**axi_chan_sva.sv L243-256（bind SVA）**：`r_beat_idx_r` 是**单一、r_id 无关**的
连续计数器，`r_active` 仅由 `r_last` 翻转；`exp_len` 从 `ar_len_q` 队首弹出。代入：
- 185 id8(last)：idx=2，弹 id0 的 len=3 ⇒ `RLAST beat index 2 != AxLEN 3`。
- 205 id0(last)：ar_len_q 已空（atop **无 AR**、从未入队 len），`exp_len` 取默认
  0 ⇒ `RLAST beat index 1 != AxLEN 0`。

——与诊断卡报告的具体错误字面**逐字吻合**。这证明：**四路证据不是四个独立信源，
而是同一个"R 不交织"重建假设在四处的同一次失效。** 诊断卡称此 SVA"独立于 UVM
monitor、纯通道接口"——它确是 bind SVA 而非用 UVM monitor，但它**自带内部计数
状态**（`r_beat_idx_r`/`r_active`/`ar_len_q`），且该状态**内建了"R 永不交织"的
前提**，故它**不是**对 DUT 的独立佐证，而是与 monitor **共模**同一缺陷。

**关键否证：物理层无任何数据丢失或截短。** 逐拍表显示 id0 实收 4 拍
（165/175/195/205）、id8 实收 1 拍（185，last）——**线上计数全对**。所谓"截短/
悬挂"纯由 monitor 误归属产生。诊断卡**未**给出任何逐拍 r_data 与参考值的比对，
即**无**独立于重建的真实数据错误证据。

裁决：四路症状**不指向 DUT**，全部可闭合为 TB 重建在合法交织下的误报。

## 正面回答 orch 追加四问

1. **PULP 为什么"会有这种缺陷"？** —— **前提不成立：这不是缺陷。** atop 注入
   只承担一件事——防 AR 计数器在原子读无对应 AR 时下溢（demux.md L83-87）；它
   **本就不打算**参与跨端口 select 保序（RTL L618 证实 inject 不写 `mst_select_q`）。
   因不同完整 ID 的响应交织**被设计明文允许**（mux.md L18），该"不参与"**不产生
   正确性危害**。既非"实现漏了一步"，也非"撞到设计假设之外"——是**设计者明确
   知道且明文承认的取舍**（见问 2）。

2. **上游文档是否暗示影子读本就不入同桶保序、是已知取舍？** —— **是，明文承认。**
   demux.md §Atomic Transactions 直言：注入是为防下溢，且"as only a part of the
   AXI ID is compared... **atomic loads can lead to additional false conflict
   stalls on the read channel**. However, atomic transactions are short bursts...
   **should not reduce throughput**"。上游把这一交互的后果**明确框定为"额外的
   假冲突 stall（吞吐/性能）"**，而**从不**把它框定为正确性问题。这与 spec §6.5
   "只影响是否 stall、不影响功能正确性"完全一致。故"交织"是这一**已知取舍**在
   `r_ready` 恒 1 的极端时序下的副作用，**upstream 不会认为它是 bug**。

3. **我们的激励是否已在 DUT 合法使用范围之外？** —— **没有，激励合法。** §6.4
   只要求 ATOP **完整 ID** 与所有在飞事务不同；0x08≠0x00 满足。低位桶碰撞是
   §6.5 **明文预期**的构造（"低位同桶假冲突"），上游 doc（demux.md L87）也把它
   当正常情形讨论。**但应如实记一句**：这是**我们主动构造出来撞的角落**（诊断卡
   亦承认次序与 §6.5 描述相反），**不代表典型使用会踩上**；典型使用中 atop 与
   普通读低位桶碰撞概率低、且真碰上时 DUT 也只是（合法地）交织或（合法地）stall。
   此点写进 TB_BUG 记录的 `## similar`/rationale 即可，不改变 TB_BUG 定性。

4. **交织是否上游特别允许？** —— **是，且是明文允许，不是但书式例外。** 穷尽
   vendor/axi/doc/*.md：唯一的交织禁止是 **W beats**（xbar.md L105 / demux.md L14）；
   对 **R/响应**，mux.md L18 反过来把"enable a slave module to **interleave the
   responses**"当作**性能收益**来讲。**许可来源穷尽，未见任何禁止 R 交织的条款，
   反见明文允许**——这句话本身即判据的一部分，据此蒸馏时并无漏掉的但书；诊断卡
   引的"禁止读交织"在许可来源里根本不存在。

**据此，issue 措辞问题不成立——不该发 issue。** 既非"你们仲裁器没考虑这个组合"
（他们考虑了，且明文当作性能取舍），也非"你们实现与自己文档另一处承诺矛盾"
（实现与文档一致：都允许 R 交织）。**唯一矛盾在我们 TB 的假设与我们自己钉定
spec/上游文档之间**——那是 TB_BUG，归内不归外。

## 六问（workflow/review.md）

1. **Origin（溯源）**：命中的三个 checker（MON_RNOAR、SVA_RLAST_LEN、SB_RBEATS/
   SB_ATOP_DANGLING）**无 spec 出处支撑其在本场景的判决**——它们隐含"R 永不交织"，
   而 spec §5.1.4/§5.5.3 允许、§5.5.4 明文禁止此类断言。**溯源失败**⇒ 检测点缺陷。
2. **Falsifiability（可证伪）**：这些 checker 在合法交织下**必红**（已见），说明它们
   **能红**；但"能红"不等于"红得对"——它们在**合法**行为上红，属假阳性，是
   decoration 的反面（过度约束）。Q2 的经典 tell（期望值来自被测 RTL）此处变体为
   "期望值来自一条 spec 未载的臆想约束"。
3. **Replayability（可重放）**：诊断卡首行给了 `make run TEST=m3_at02_atop_read_test
   SEED=1 FSDB=1` + 一行激励改动（len_t'(0)→len_t'(3)），工作区已还原、可重放。✓
   （但复现的是**假红**，非 DUT 缺陷。）
4. **Attribution（归因）**：诊断卡 first_anomaly 落在 R 通道交织窗口，但**归因到
   DUT 错误**；我复核后 first_anomaly 的**因果链应止于"合法交织 + TB 无交织重建"**，
   taxonomy 由 DUT_BUG 改判 **TB_BUG**。closer≠fixer 在后续 TB 修复+复跑时仍须遵守。
5. **Judgment（判断）**：现有证据**不支持** DUT_BUG。缺口清单：①无逐拍 r_data 与
   参考值比对（无真实数据错误证据）；②未把"R 交织是否被 spec 允许"与"beat 序是否
   为真"分开判断；③把共模 TB 假设当作独立信源。
6. **Retention（沉淀）**：教训须落成守卫——**r_id 感知的 R 重建**（monitor 逐拍按
   r_id 分流、SVA 按 r_id 分别计数）+ 一条**多拍 atop×并发同桶异目标读**的定向
   交织覆盖/测试，作为 TB_BUG 的 regression_guard；BUG-0034 详情页须记 §5.1.4/
   mux.md L18 作为"交织合法"的钉子，供第三次遇到时分钟级定位。
7. **Kill coverage（击杀）**：本卡为仲裁、不签 milestone，不逐类点名 KILL。但提示
   签核卡：R 重建 checker 修好后，其**可证伪性**应有一次 KILL 自证（合法交织→绿、
   注入真交织越界→红），因为当前该类 checker 的"红"全是假阳性、从未证明它能对
   **真**缺陷见红。
