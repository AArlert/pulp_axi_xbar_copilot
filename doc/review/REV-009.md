## 2. 评审范围逐项 verdict

### 2.1 behavior-leak 门禁 —— pass

两行描述均停在"验证什么可观测行为"：M2-OR03 判据落完成序（§5.2.3）与两处
非判决 cover（BUG-0023/BUG-0024 各自的"角落是否被触达"，非新判决）；M3-TL01
判据落 scoreboard 正确性 + 非判决 cover（合计在飞数状态）。"使核心判决逻辑
解除 stall"一语是**刺激构造手法的说明**（为提高 BUG-0023 同沿巧合概率），
不是判决条件本身——判据 (1) 未依赖它，明文"不强行断言具体拍数"。无泄漏。

### 2.2 判决锚点延迟不敏感性 —— pass

两行均未出现"第 N 笔在某具体时点/拍数被接受或拒收"式表述；M2-OR03 甚至
显式引用 SPEC-7.4.5 自我约束"不强行断言具体拍数"。BUG-0023 的同沿角落
（`w_collide_q`：`aw_id==b_id` 同拍）是**非判决 cover**，观察"是否恰好撞上
同一拍"本身不是判决——这与 BUG-0013 先例（"接受边界"字面前提留作 cover、
不升格 assert）同构，合规。

### 2.3 守卫有效性 —— conditional（本卡核心发现）

**方法**：亲读 `tb/sva/axi_xbar_stall_sva.sv` 全文，逐条对照两条 bug 的
`regression_guard` 段与该文件的实际判决/cover 机制，而非假设"testplan 行
写了就等于能守住"。

**BUG-0023 角落（同沿 `aw_id==b_id` 写冲突）—— 可有效证伪，机制已就位**：
该角落的检测侧信号（`w_collide_q`/`w_collide_kept_now`，L164-178/257-259/
307-310）**纯自引用**（同一 ID 自己的 AW 接受与 B 完成撞同一拍），不依赖任何
第二个 ID。DV 已实测这 4 条 cover 喂现有 9 个场景命中数全 0（BUG-0023 页
`## regression_guard` note-2），量化确立了"现有激励绕开、需新场景"的结论。
M2-OR03 的构造（单一完整 ID、同目标堆积后切换目标）恰好是使
`aw_id==b_id`（第三笔 AW 接受撞上 A 组某笔 B 完成）有机会发生的正确形状。
**结论：这部分守卫机制已存在、只待定向激励接入，pass。**

**BUG-0024 角落（单 bit 容量不足）—— 现有机制无法观测，存在真实缺口**：
逐读 `w_sibling_open()`（L189-199）与 `w_reorder()`（L218-228）：两者的
候选集枚举**显式排除自身**（`cand != id` / `cand != completing_id`，
L196/223），只遍历**低位相同、完整 ID 不同**的"兄弟"ID（`sibling_id()`，
L182-185）。也就是说，该模块当前**从未**、也**不会因把 `w_id_open` 换成
计数器而开始**检查"同一个完整 ID 自己的多笔在飞记录是否正确"——这条信息
只在**另一个兄弟 ID** 查询该 ID 的 `w_id_open[cand]`/`w_id_tgt[cand]` 时
才会被读取。BUG-0024 的症状（同目标堆积第 2 笔的记录被第 1 笔完成提前清除）
只有在**存在一个共享低位、正在被检查的兄弟 ID** 时才会对本模块的任何
assert/cover 产生可观测差异。

M2-OR03 的构造描述是**单一完整 ID `X`**（testplan 原文："单 slave 端口、
单一完整 ID `X`"），全程不出现第二个（哪怕是共享低位的）完整 ID。按上述
代码结构，这一构造**不会触及**该模块现有的任何 sibling 相关 assert/cover
——即便 BUG-0024 修复把 `w_id_open` 换成计数器，`sibling_id()`/`w_reorder()`
的自排除结构不变，"计数是否正确"这件事本身**在现有信号里无处可读**。

testplan 行判据 (2) 要求的 "至少一次观测到『同一完整 ID 有 ≥2 笔同目标事务
同时在飞、且另一笔异目标同 ID 事务处于待转发状态』" 这条覆盖，**必须依赖
修复卡新增一个自引用（per-full-ID，不经 sibling 枚举）的可观测量**（例如
直接暴露"该 ID 当前在飞笔数"的计数器信号供 cover 采样）才能被满足——这不是
"多写一行 cover 接现有信号"能完成的，而是需要新的检测侧结构。这与
`doc/bugs/BUG-0024.md` `## regression_guard` 自身标注的 `ref: 待定（修复卡
落地时确定）` 一致（该页作者也未预设机制），但 M2-OR03 的 testplan 描述
（正确地，遵循 behavior-leak 纪律）未点破这一点，容易让下一个读到 "🔲" 状态
误以为"接现有 4 条 cover 再加激励即可"。

**裁决**：这不构成对 testplan 行本身的驳回（arch 保持实现无关的描述是
正确姿态，不应在 testplan 里预写检测侧结构），但构成一条必须写入派发条件
的事实缺口——DV 落地此卡时必须知晓：BUG-0024 的 (2) 覆盖不能复用现有
sibling 信号，需要新设计一个自引用的检测点，并且必须像 BUG-0023 那样
**量化验证**它在"未修复"状态下确实不可命中（或结构性论证其在修复前必然
为 0）、在"已修复+已激励"状态下确实可命中——否则 (2) 项覆盖会退化为"空转
场景"（rubric 第 5 条精神：a guard that has never been seen red is a
hypothesis）。

**BUG-0023 cover 侧的次要观察（非阻塞）**：同沿撞击是"自然运行下有机会"
（testplan 原文），属概率性构造。鉴于这是一个**定向**场景（非随机流量），
建议 DV 落地时用确定性同步（如显式等待特定握手拍再发出第三笔 AW）而非纯
依赖概率碰撞，以避免守卫本身对种子敏感、需要多轮迭代才可能见证——非阻塞，
落地细节留给 DV。

### 2.4 合并/拆分判断 —— pass（同意 arch 的取舍）

亲读三份 bug 详情页原文后独立判断：

  testplan 行"——arch 的合并决定与 bug 作者自己的建议一致，且合并后的单一
  场景确实能承载两个角落各自的判据/cover（§2.3 已验证结构上是"能否观测"的
  差异，不是"该不该合并"的差异）。
- **BUG-0010 保持独立为 M3-TL01，同意**：BUG-0010 是**完全不同的机制**
  （§5.4.1 事务数上限的跨桶聚合规模问题，SPEC_ISSUE/仲裁已定分桶口径，涉及
  `axi_xbar_txlimit_sva.sv`），与 stall_sva 的 TB_BUG（BUG-0023/0024，
  §5.2 保序 checker 内部缺陷）在 bug 类别、涉及子模块、许可来源、里程碑
  归属（BUG-0010 自身 `## regression_guard` 明文"此守卫随 M3/M4 规划落地"）
  上均无交集。若强行合并到 M2-OR03 反而会把两类完全不同性质的判据混进同一
  场景描述，违反"一个场景一个可证伪主张"的清晰性。**拆分正确。**
