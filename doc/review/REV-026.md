## rst_ni（F-2）独立裁决

**独立结论：采纳 Option 1（CW-006 Kind-A 范围豁免），驳回 Option 2 作为主处置。** 我的理由与 arch 部分重合，但落点独立：

1. **未定义恢复语义是实质红线风险**：spec §2.3 仅"rst_ni 异步、低有效"（`doc/spec.md` L90），五份许可来源皆无"在飞事务遇复位去向 / 复位释放后内部计数器·FSM 恢复语义"。M4 引入带在飞事务的热复位，checker 对"复位后在飞事务应如何"的期望**只能来自 RTL**——spec-from-RTL 越界。同 BUG-0002/0003/0032 的未定义→范围约束先例。
2. **Option 2 是 toggle-theater，独立驳回**：arch 的 Option 2 构造性保证零在飞，因此**永不测试**任何复位恢复语义——它纯粹为翻 `rst_ni` 1→0 这一位而造场景。为覆盖率位本身造场景违反"目标即门"（`workflow/discipline.md`）：一个判决门只落"复位后新事务正确（=M1-01 判据）"、复位脉冲本身不被判决的场景，其覆盖数字不对应任何有意义的复位验证。诚实记账（豁免）优于制造这样的数字。
3. **范围豁免有直接同构先例**：CW-002（scan `test_i` 范围外，Kind-A，**无 bugs.md 行**）是最贴近的先例——scan 与运行中复位同为"项目验证范围未纳入"的结构位。按 CW-002 形状登记 **CW-006（Kind-A：`rst_ni` 1→0 四模块 toggle；范围外理由 = 运行中复位恢复语义许可来源未定义；可证伪解锁 = 验证范围纳入运行中复位 **且** 先补齐复位恢复语义 spec 条款）**，rev 记录引本裁决 + REV-025。

**对 arch 的 spec 微改提案（§2.3/§7 加范围声明）**：**原则批准，但降级为独立 spec-change-proposal，不作 CW-006 的阻塞前置**。理由：按 BUG-0032/REV-012 的 Retention 先例（约束须落 spec 正文、非仅 guard/waiver），§2.3 平行加一条"运行中复位恢复形态许可来源未定义、验证范围不含运行中热复位"确属正确归宿。但 CW-006 豁免可**立即**基于 CW-002 先例 + 现有 §2.3 文本登记，spec 正文条款走常规 rev spec-review 门禁（如 REV-013 对 P-REV012-1 那样逐字审）后由 orch 应用、重 pin——**两步解耦，豁免不等 spec 条款落地**。exact wording 由 orch/arch 拟，rev 不代写（编号建议 P-REV026-1）。
