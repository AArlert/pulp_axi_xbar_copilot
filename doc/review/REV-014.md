**核验结论**：DUT 实际驱动 `r.data = data_t'(64'hCA11AB1EBADCAB1E)`。基线 `AxiDataWidth=64`（spec §0，L23）⇒ `r.data = 64'hCA11AB1EBADCAB1E`——与 DV 实测 `'hca11ab1ebadcab1e` 逐位吻合。文档 L33 的 "`32'hBADCAB1E` 零扩展（高 32 位 = 0）" 与实现的高 32 位 `0xCA11AB1E` **互相矛盾**。BUG-0033 详情页/行内对原文、行号、机制的转述**经 rev 独立逐行复算，一致无误**。

**关于宽度依赖（rev 追加核验，DV 未展开）**：矛盾的严格形态取决于 `AxiDataWidth`——
- `AxiDataWidth=64`（基线）：`r.data = 64'hCA11AB1EBADCAB1E`，高 32 位 `≠0`，**与文档矛盾**。
- `AxiDataWidth=32`：`r.data =` 截低 32 位 `= 32'hBADCAB1E`——此时文档 L33 **恰好正确**。
- `AxiDataWidth=128`：`r.data =` 零扩展 `= 128'h0…0_CA11AB1EBADCAB1E`。

即文档 L33 只在 32 位宽情形下正确：它把 err_slv 的 64 位默认 `RespData` 误记成 32 位，又把 32→64 的零扩展当作全部行为。真正的机制是"**64 位常量 `RespData` 按 `AxiDataWidth` 零扩展/截断**"——L33 的"zero-extended or truncated to match data width" 措辞本身对（追溯 `RespWidth` 适配），**唯一错的是基数值** `32'hBADCAB1E`（应为 `64'hCA11AB1EBADCAB1E`）。此点决定校正应保持宽度参数化，不得把 §4.4 硬写死成 64 位常量。

## 2. Taxonomy 终判：**SPEC_ISSUE**（不改判 DUT_BUG）

成本阶梯 `TOOL_ENV → TB_BUG/CONSTRAINT_BUG → SPEC_ISSUE → DUT_BUG` 逐级排除：

- **TOOL_ENV — 排除**：现象根因是 RTL 常量默认值（结构事实，只读快照不可伪造），与 seed/机器/编译期异常无关。
- **TB_BUG / CONSTRAINT_BUG — 排除**：checker 期望 `ERR_RDATA = data_t'(32'hBADCAB1E)` **忠实蒸馏自 spec §4.4**（其自身出处 xbar.md L33），非照抄 RTL；激励为 directed（未命中地址读，无约束）；同批 resp 码/beat 数/`RLAST`/下 32 位/路由回送全过——唯读数据高 32 位失配。非 TB 侧缺陷；DV 的输入边界纪律到位（**未**把观测值 `CA11AB1E` 搬进 checker，spec-from-RTL 红线未破）。
- **SPEC_ISSUE — 命中，且 DUT_BUG 未被挣得**：见下。

**为何是 SPEC_ISSUE 而非 DUT_BUG（举证：清空一切之后仍未归咎 DUT）：**

1. **被违反的不是任何显式协议条款，只是上游自家散文。** taxonomy 的 DUT_BUG 判据是"DUT output violating an **explicit spec clause**"。AXI4 **不规定**错误响应（`RRESP=DECERR`）读数据的具体值——错误响应的 `RDATA` 是 don't-care，master 依协议应忽略之。DUT 吐出 `CA11AB1EBADCAB1E` 不违反任何 AXI 显式条款；它"违反"的仅是 vendor **自己文档** L33 的散文，而**同一 vendor 的 RTL 默认常量正是它自己的反例**。据 discipline rule 1，"文档写零扩展⇒零扩展即意图⇒RTL 有 bug" 是被明令禁止的反向臆断——无独立证据表明散文（而非 RTL 常量）才是上游意图。

2. **正面证据支持 RTL 常量才是意图。** `RespData` 默认值 `64'hCA11AB1EBADCAB1E` 是一个刻意构造的 leetspeak 魔数（`CA11AB1E`≈"CALLABLE"、`BADCAB1E`≈"BAD CABLE"），显然是设计者有意选定的完整 64 位标记；而文档 L33 只记住了低半 `BADCAB1E`、把高半误述为零扩展。矛盾的合理解释是**文档陈旧/不精确**，不是逻辑缺陷。

3. **零功能/协议损害。** 同批 scoreboard 的 resp 码、beat 数、`RLAST`、响应回送、写路单拍 B 全绿，唯读数据高 32 位差异，且该数据在协议上本就 don't-care。无任何错误的可观测协议行为。

4. **与 BUG-0016 同签名。** 上游文档与其自身实现相抵触、DUT 在"该值只是内部默认标记常量"读法下完全站得住——SPEC_ISSUE 的教科书判据（"spec 与上游文档相抵触；DUT 与 TB 各自在不同读法下都站得住"）。

**与 BUG-0032 的辨析（本卡明确要求）**：二者同处 §4 err_slv 邻域、同属 taxonomy SPEC_ISSUE，但**处置分道**——
- BUG-0032 = **许可来源沉默**（err_slv×ATOP 应答形态 undefined）⇒ 处置 = 保留"未定义"+ 环境约束构造性回避（REV-012/013）。**不能**改判为某个具体值，因为没有权威值可写。
- BUG-0033 = **许可来源明确但与 RTL 矛盾**（contradiction）⇒ 存在唯一的、只读不可改的权威事实（RTL 常量）⇒ 处置 = 以 RTL 为准校正 spec（同 BUG-0016）。
故本卡**不套用** BUG-0032 的环境约束路径，而走 BUG-0016 的 SPEC_CHANGED 路径。这是两条不同的 SPEC_ISSUE 处置，非同一模板。

**结论：taxonomy 终判 = SPEC_ISSUE。DUT_BUG 不予签核**（DUT 无错误协议输出、且对该值持一个由 RTL 结构完全支撑的另一读法"内部默认标记常量"；"blaming the DUT earned by eliminating everything else"——更便宜的 SPEC_ISSUE 解释非但未被清空，反而证据更充分）。**不走 P-xxx 行为补丁**：既未签 DUT_BUG、行为亦协议合法，任何本地改 `RespData` 都是把 TB 的字面读法强加给 vendor IP（discipline rule 1 反向臆断），禁止；且无行为可改。

### P-REV014-1 — spec §4 clause 4（读响应数据值）校正

**原文**（`doc/spec.md` §4 第 4 条，L148）：
> 4. 读响应每个 beat 的数据为 `32'hBADCAB1E`，按数据宽度零扩展或截断。

**新文**（实质，宽度参数化——保留 L33 正确的"零扩展/截断"机制、仅校正基数值）：
> 4. 读响应每个 beat 的数据 = err_slv 的默认参数 `RespData = 64'hCA11AB1EBADCAB1E`（`RespWidth=64`；`axi_xbar_unmuxed.sv:195/238` 两处例化 `axi_err_slv` 均**未覆写** `RespData`/`RespWidth`，故取此默认），SV 赋值 `r.data = RespData` 按 `AxiDataWidth` **零扩展（更宽时高位补 0）或截断（更窄时取低 `AxiDataWidth` 位）**。基线 `AxiDataWidth=64` ⇒ `r.data = 64'hCA11AB1EBADCAB1E`（下 32 位 `0xBADCAB1E`、上 32 位 `0xCA11AB1E`）；`AxiDataWidth=32` ⇒ 截为 `32'hBADCAB1E`。**（来源：RTL——`axi_err_slv.sv:24-25`、`axi_xbar_unmuxed.sv:195/238`；上游文档 xbar.md L33 把基数记作 `32'hBADCAB1E`、上 32 位零扩展为 0，与 err_slv 实际默认 `RespData` 高半 `0xCA11AB1E` 不符——L33 仅在 `AxiDataWidth=32` 截断情形下恰好正确。BUG-0033 裁决 REV-014。）**

**rationale**：§1(a-f) + §2。文档 L33 的"zero-extended or truncated to match data width" 措辞正确追溯 `RespWidth→r.data` 适配机制，唯一错误是基数值——它是 64 位标记常量而非 32 位。校正必须保持宽度参数化（§1 追加核验：32 位宽下文档恰对），不得硬写死 64 位常量，否则将在非 64 位配置矩阵项（spec §0）上产生新的无源期望值。标注"来源：RTL——文档不符"符合 CLAUDE.md §6"仅有 RTL 来源的条款须标注来源"及 REV-007 先例。**spec-from-RTL 边界说明**：此处以 RTL 常量校正 spec 属**仲裁结论**（doc-vs-RTL 矛盾经 rev 独立裁决、以只读权威事实为准），非 DV 私自抄 RTL 入 checker——两者的区别正是 discipline rule 1 的要害；校正后 checker 期望仍从 pinned spec §4.4 推导，不从 RTL 直取。
