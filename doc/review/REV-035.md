#### Q3(c) 裁决：**立一条 `script` 类 guard，不是 `checklist`**

- **guard 契约四字段的形状**（原则与方向，不写实现）：

    note**，否则下一位只扫 `doc/review/`。

  rev 实例在写自己的记录时**当场复现了同一泄漏**并自检删除。同一陷阱在相邻两张
  卡上各触发一次 ⇒ 写作陷阱，非一次性疏忽。

### Q5 — 共同根因与系统性防线

**族的辨识**（本卡确认 bug 行的归族陈述成立）：BUG-0049（漏账：格 → 无归属）·
BUG-0050（超额认领：引用面 ⊋ 登记面）· BUG-0051（事实错抄：声明性文本 ⊥ 机器
事实）。共同根因：**覆盖账目的声明性文本与其所依据的机器事实之间没有机器核对**。

**裁决：值得一条族级 guard，且它应当"承载"而非"叠加于"三条各自的 guard。**

- **理由 1（判据同形）**：三条的判据是**同一个形状** —— 从声明性文本解析出一个
  集合，从机器事实解析出另一个集合，求差，差非空即红：
  - **D1** `格 ∖ 归属` = UNOWNED（BUG-0049 面）
  - **D2** `引用 ∖ 登记` = 越权引用（BUG-0050 面）
  - **D3** `声明 ∖ 报告实有` = 事实错抄（BUG-0051 面：N/A 成因所声称的类型集合、
    以及实例数标量）

  三条分散的 checklist guard 会是同一句话说三遍（`workflow/discipline.md` §2）。
- **理由 2（消费面同一）**：三条的 `paths:` 都指向
  `doc/coverage-waivers.md` / `doc/evidence/**` / `milestone_restructure.md` §6
  这同一组文件。分散 guard 会让 `make guards` 在同一张卡上打印三段近似文本，稀释
  注意力 —— `doc/evidence/**` 上已经叠了 BUG-0008/0026/0029 三层，本卡就吃到了
  这个体验。
- **理由 3（可机械化度一致）**：三条**都**能机械化，且落在**同一份原始数据**上
  （`sim/out/urgText6/{modlist,modinfo,hierarchy}.txt` + 三份声明性文档）。若三者
  机械化难度不同，分散才更合适 —— 这里不是。

**判据形状（原则与方向，不写实现）**

1. **一条命令，三个差集，一个退出码。** 输出签名可粘贴（REV-034 §G6 已把 D1 压成
   过 `RESULT CELLS=132 LT90=30 UNOWNED=0` 这个形状；本 guard 是把 D2/D3 加进
   同一条命令）。
2. **输入白名单是判据的一半，必须写死**：只准 ①原始 urg 文本报告

## Guidance（原则与方向，不写实现）

**G1 — "不回改"保护的是真话，不是错话。**
FB-23 的保护对象是"写作时为真、因外部改名而失效"的陈述；它自己的措辞就写着
"不是谁做错了"。一条被自己援引的数据源当场证伪的陈述不在这个保护面内。但落盘
公理仍然管用 ⇒ **不覆写、只批注**。可引用的边界：**不回改 = 不覆写、不删除；
不等于不许批注。** 加标记是加法（保留全部原信息 + 新增一条指针），覆写是减法
（销毁"当时相信什么"这一信息）。判断一处该走哪条路，问一句：**删掉它，未来
读者会失去可读的信息吗？**

**G2 — 授权以登记行自身为准，引用方不能替它扩权。**
这是 `doc/spec.md` §0#4"判定单位 =（模块,类型）二元组"+ BUG-0038"不得以父模块
豁免代表子模块"的直接推论，也是 CW-010/012/013 已在用的写法。**但"补齐一致"有
两个方向，选哪一侧不是对称问题**：看**哪一侧有独立的在先裁决支撑**。CW-002 扩
登记（删引用会制造孤儿格）· CW-007 删引用（扩登记会推翻 REV-031 的明确裁决）。
一刀切成"都扩"或"都删"都会出错。

**G3 — 债务行作为归属面，缺的不是文档义务，是 guard 的消费面。**
不要给 `ACCEPTED@M<n>` 行发明一个 spec 里没有的自述字段 —— 那是加义务。正确的
方向是承认既有耦合并让**既有机制**（`make guards`）承担它：一条 guard 的 `paths:`
是它的**作用域**，不是它的出生地。BUG-0044 的 guard 现在只守一条消费路径
（随机化放宽），漏了第二条（债务行状态变化使覆盖率归属失效）。**guard 的判据永远
是那一句：如果这个缺陷明天原样再来一次，哪个检查先红？**

**G4 — N/A 的成因是判定要件，"删掉错句"不是修复。**
`doc/spec.md` §0#4 让 N/A 不进分子分母，代价就是必须给出**经核实的**结构成因。
一条成因合格与否的检验是**正向**的：原始报告要能支持它，而不只是"直觉上说得通"
或"没被明显推翻"。更强的一条：**成因背后的判别式必须在全闭包上自洽** —— 它要能
同时解释"哪些模块有该类节、哪些没有"两侧。只解释一侧的规则（如脚注 4）在下一格
就会失效，而失效时没人会发现，因为它上次"看起来对"。

**G5 — 能机械化的 guard 不要写成 checklist。**
`workflow/bugs.md` 说 checklist guard 是**机械化 TODO**。把一扇今天就能关的门写成
TODO，等于把它留开并给自己一个已经尽责的感觉。同理，**新入口不是新守卫** ——
挂进已被每张卡消费的 `make check`，比新建一个正确但没人跑的脚本强。

**G6 — 同形判据合并，异形判据分开。**
三条 bug 是否共用一条 guard，判据不是"它们看起来同族"，而是**三个具体的问题**：
判据形状同不同？消费面（`paths:`）同不同？可机械化难度同不同？三个都"同"才合并。
合并后每条 bug 的 `note:` 仍须各写各的分量 —— 合并的是**实现**，不是**教训**。

**G7 — 核对的输入白名单是判据的一半。**
BUG-0049 的成因不是复核者不认真，是**两级复核都拿汇总清单当输入**。一条以汇总为
输入的核对，核的是"抄得一致"，不是"抄得对"。任何以"防止账目失真"为目的的检查，
**必须在输入侧禁掉被检对象的汇总面**，否则它只会把错误固化得更快。
