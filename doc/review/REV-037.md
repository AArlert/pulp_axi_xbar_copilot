### BUG-0055 — tag 命名空间与上游冲突 → **修**（处置面已由 principal 裁定，本卡只转可执行终态）

**核对结论：现象成立，且比行内所述更干净。** 台账 F/G。

**(1) 机器判据（本卡的核心交付，不是人工列举）**
```
ours(t)   := git merge-base --is-ancestor "$(git rev-parse "$t^{}")" master
theirs(t) := git merge-base --is-ancestor "$(git rev-parse "$t^{}")" upstream/master
```
实测在全部 24 个 tag 上，`ours` 与 `theirs` **恰好互斥且完备**（5 / 19，无同真、
无同假）。故该判据可作为唯一分类器，无需枚举名单。三点须写进 fixer 卡：
- **不得用 tag 对象类型判别**：`v0.4.0`/`v0.4.2` 是 annotated tag 却属本项目，
  `v0.1.0`/`v0.2.0`/`v0.3.0` 是 lightweight 却也属本项目——类型与归属无关。
- **必须先 `^{}` 剥离**再判祖先，否则 annotated tag 的 tag 对象不是任何 commit 的祖先。
- **`refs/remotes/upstream/master` 缺失时判据须 fail-closed**（报红并停，不得跳过）。

**(2) 本卡实测的新事实（行内没有，直接决定动作范围）**：`git ls-remote --tags origin`
只返回 5 条项目 tag ⇒ **19 条上游 tag 从未推送到 origin**。因此删除是**纯本地
操作**，无需 `git push origin :refs/tags/<t>`，也不存在删掉已发布 tag 的风险；
且删除后 `git fetch origin` 不会把它们带回来——只有 `git fetch upstream` 会，
这正是 `--no-tags` 要堵的口。

**(3) 复验签名**
```
S1  git tag | wc -l                                                   → 5
S2  for t in $(git tag); do ours($t) || echo BAD; done                → 无输出
S3  for t in $(git tag); do theirs($t) && echo LEAK; done             → 无输出
S4  git config --get remote.upstream.tagOpt                           → --no-tags
```
**证伪程序**：`git tag v0.5.0 fb2c193` → S1/S3 必红；`git tag -d v0.5.0` → 复绿。
`git config --unset remote.upstream.tagOpt` → S4 必红；恢复 → 复绿。

**(4) `.git/config` 侧改动写进 CLAUDE.md 的哪一处**：§5「每次 clone 后执行两条
一次性设置」的**第二条**——`git remote add upstream <url>` 改为
`git remote add --no-tags upstream <url>`（该写法即在 `.git/config` 的
`[remote "upstream"]` 下落 `tagOpt = --no-tags`），并补一句"既有 clone 补执行
`git config remote.upstream.tagOpt --no-tags`"。同段「跟进上游」那句的
`git fetch upstream` 建议一并写成 `git fetch upstream --no-tags`（双保险，且不
依赖 `.git/config` 已配好）。CLAUDE.md 属本仓库自有 ⇒ **不需要 FB 行**。

**(5) 三处文档是否仍需订正——逐处实测后：全部不需要**
- **`doc/milestone.md`：不需要，且行内对它的指控不成立。** 本卡 `grep -n

——卡片的转述准确，措辞属实。

**(b) 是否落地：否，且连载体都不存在。** 三条独立证据：
1. **无实现**：`grep -rln "UNOWNED=" scripts/ sim/ Makefile` 零命中；仓内不存在
   任何产出 `RESULT CELLS=… UNOWNED=…` 形状的脚本（该字串只出现在 `doc/` 的
   散文里）。
2. **无归属载体**：REV-035 §Q5.3 规定"三条 bug 各自的 `## regression_guard` 的
   `ref:` 指向同一实现"。但 BUG-0049/0050/0051 已 CLOSED 并归档
   （`doc/archive/bugs-archive.md:8/:6/:5`），且**三者都没有详情页**
   （`doc/bugs/BUG-0049.md` 等均 `test -e` 失败）⇒ **三条根本没有
   `## regression_guard` 段**，§Q5.3 那条规定在今天**无法被满足**。
3. **无消费**：因 (2)，`make guards` 对任何文件都不可能打印这族的教训——
   七问 Q6（Retention）在这族上**当前载体为零**。

**(c) 若建，应是什么形状**：REV-035 §Q5 已写死，本卡确认无须改动——一条命令、
三个差集（D1 `格∖归属`、D2 `引用∖登记`、D3 `声明∖报告实有`）、一个退出码；
输入白名单钉死为①原始 urg 文本报告 ②`doc/coverage-waivers.md`
③`doc/bugs.md` 的 `ACCEPTED@M<n>` 行 ④`milestone_restructure.md` §6，**禁止**以
`M4-coverage-final-sweep.md` 的汇总节为输入。

**(d) 由谁落地**：REV-035 §Q5 已指派——"一张独立的 tooling 卡（L1/L2）"，
"**应排在 M4 签核卡之前**"，且明确**不是**三条 bug 关闭的前置。三条已按该裁决
关闭，程序无瑕。**但那张 tooling 卡从未派出**，而本批 14 条一旦收口，下一张就是
M4 签核卡 ⇒ 该排期约束**即将到期**。

**(e) 本卡的处置**：不把它设为本批 14 条的前置（那会违反 REV-035 的裁决与
"小闭环即停"），**但把它设为 M4 签核卡的前置**。依据：rubric #6"未见过红的
guard 是假设不是 guard"，与七问 Q6——今天这族的 Retention 载体是**零**，而
M4 签核书必须回答 Q6。

**(f) 与 §1 各条"修"的承载关系（卡片点名要求）**：
- **BUG-0063 与 BUG-0064 就是 D3（`声明 ∖ 报告实有`）的两个新实例**。因此本卡
  给这两条规定的签名形态**刻意与 D3 同构**：一行一个事实、值从
  `modinfo.txt`/`modlist.txt` 原始报告重算、写进已存在的 §10.5 `ERRATA-FACTS`
  块。这样它们是 REV-035 所说的"**零件**"，将来 tooling 卡把 §10.5 整块纳入
  D3 的输入即可，**不重复劳动**；若改用一次性 `grep`，就变成叠加而非承载。
- **BUG-0061 的"零匹配即告警"是同一形状的第四个差集**（`声明 paths ∖ 实际匹配
  文件`）。建议 tooling 卡把它编为 **D4** 一并承载，而不是让它长成第四个独立脚本
  （否则就是 REV-035 §Q5 理由 1 点名的"同一句话说三遍"）。
- **BUG-0052 的死引用检查是第五个同形差集**（`文档声明的仓内路径 ∖ 实存路径`）。
  它落在 `docs-check` 而非覆盖账目上，与 D1–D4 的输入面不同，**本卡判定不并入
  族级 guard**——REV-035 §5 自己给的可证伪点即"若三个差集中任一落在不同的原始
  数据面上，族级合并即作废"，此处正是"不同数据面"，故分开是遵守而非违反。
- **前置**：(b)-2 指出的详情页缺失（§3 发现 B）**必须先解决**，否则族级 guard
  连 `ref:`/`paths:` 都无处可写。

     则"31 不成立"这一判定需重议（本卡已用两种口径互证：57 对 / 53 号）。

## §7 总体裁决

**通过（有条件）** —— 本卡对 BUG-0052 ~ BUG-0065 十四条给出**逐条终态裁决，
无一条留空或待定**：**14 条全判"修"，零 `ACCEPTED@M<n>`，零 `WONTFIX`**；
每条附处置面、可机器执行且可证伪的复验签名、fixer 类型与级别、以及是否需要
FB 行。分组与顺序见 §5 问 2，orch 可直接据此切七张卡。

**条件（缺一则本裁决不构成 M4 签核的充分前置）**
1. **§3 的两条新行必须由 orch 先行登记**（建议 BUG-0066：`regress.py:50` 破坏性
   `make clean`；BUG-0067：23 条 bug 行无详情页 + 孤儿检查单向）。登记是无条件的
   （CLAUDE.md §2），且 BUG-0067 是本批多条 guard 能否落地的前置。
2. **每条判"修"的行在关闭前补齐 `doc/bugs/<ID>.md` 详情页**，否则本卡指定的
   guard 无载体。
3. **五条新 checker 判据各证伪一次**（§6 问 7 列名），由各自的独立 closer 执行。
4. **族级 guard tooling 卡排在 M4 签核卡之前**（REV-035 §Q5 的原排期，本卡确认
   并升格为 M4 签核前置）。
5. **在条件 1 有裁决前，全程禁止 `make regress` 与 `make clean`**。

**定级 vs 实际：一致（L3），无失配。** 本卡落在"spec/豁免/签核"面（其输出直接
决定 M4 能否签核）、rev 必到、走全 rubric，与 L3 定义相符。一点说明而非失配：
其中三条（0062/0063/0064）的核对需要从原始覆盖库文本与 vendor RTL 重算数字，
工作量属 L2 强度，但这是 L3 卡内的取证成本，不改变定级。

**本卡未做的事（边界声明）**：未修改任何代码、未修改 `doc/bugs.md` 任何列
（状态列由 `evidence.py` 回填）、未关闭任何缺陷、未改写 `doc/evidence/` 或
`doc/review/REV-035.md` 的任何字节、未执行 BUG-0055 的 tag 删除、未跑 sim、
未 `make clean`、未写入 `sim/out/`、未读取本会话 scratchpad 内其他实例的产物。
