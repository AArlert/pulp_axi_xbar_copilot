## Item 2 — §4/§5.3 自引用 spec-edit 提案

### 亲验事实

- **提案原文**（`doc/archive/log-archive.md:125-127`）：§4/§5.3 正文从不自引用
  其编号子条款，致 `chain-audit` parent-anchored 由 5 增至 15；arch 建议在正文
  补精确自引用以降该计数，交 rev 判断是否值得动 pin。
- **spec 编号惯例**（`grep -nE "^#{2,4} " doc/spec.md` 直接观测）：spec 只有
  两级标题——`##`（§0-§8 + Change record）、`###`（§2.1/§3.1-3.4/§5.1-5.5/
  §7.1-7.4）；**不存在** `§4.2` / `§5.3.1` 形态的标题。§4 与 §5.3 的条款一律
  是正文有序列表项，"§4.2"/"§5.3.1" 全程只作 inline clause reference。这是**一致
  且刻意的文体**，非疏漏。
- **parent-anchored 的成因是解析器缺陷、非 spec 缺陷**（FB-24，
  `doc/fw-feedback.md:62`，本卡复核其举证）：`chain-audit` 的 §id 解析器把"章节
  内有序列表项"当成 spec 子章节，幻影率实测 4/9 = 44%；§4 只有 `## 4.` 一个
  标题、条款 4.1-4.5 是列表项，testplan 引 SPEC-4.1~4.5，其中**恰在正文被
  inline 提及的**（§4.1/§4.5）解析成功、**未被提及的**（§4.2/4.3/4.4）跌回父级
  §4——这正是 parent-anchored 由 5 涨到 15 的机制。计数测量的是解析器口径，不是
  spec 的可追溯性缺陷。

### Verdict

**REJECTED（否决该 spec-edit 提案）。**

- **这是 content 迁就 tool，方向倒置**（discipline rule 2/3）：往已 pin 的
  spec 正文塞纯为喂解析器的编号自引用，是让被验证内容去服务观测工具。
  CLAUDE.md §4 的红线（工具只是取"实际发生了什么"的手段、期望值只从 spec
  推导）与 constitution 的 tool-serves-content 次序，都指向同一结论：spec 文体
  不该为 chain-audit 的口径让步。
- **零 content 收益**：无任何条款在实质上模糊或未被追溯——§4/§5.3 的条款已
  被 testplan（SPEC-4.x）、其它 spec 节、review 记录精确引用。唯一"问题"是一个
  工具计数器，而该计数器（FB-24 已证）测的是解析器把列表项误判为子章节的
  artifact。
- **成本非零**：动 pin = sha256 变更 + 每一份引用现 spec 的冻结记录出现口径
  漂移风险，换来的是零验证价值。
- **持久归宿是 FB-24（上游修解析器），已登记、open。** 正确修法是解析器区分
  "有标题的子章节"与"仅 inline 出现的 clause ref"（FB-24 建议①：幻影的 title
  恒空，据此过滤，改动约一行），而非本地肢解 spec 文体。

### Guidance

不要把门禁/审计工具的计数当成内容目标。当一个数字要靠改被测内容来降，先问
"这个数字测的是内容缺陷还是工具口径"——FB-24 已回答是后者。提案作者
（arch）自己在 log [0.3.5]/FB-24 也已转向建议否决，本裁决与之一致并给出正式
裁定。

## Item 3 — 三处 orch 自标越界

### 边界判据

CLAUDE.md §0 的禁令是精确列举的**四类技术制品**："orch 不产出任何技术制品：
不写 RTL、不写 TB、不写 design-prompt、不自行产出 spec 内容"。判越界的问是：
该编辑是否**产出了这四类之一的技术/行为内容**（需 arch/de/dv 判断、且 design-
prompt 内容须过 rev 行为泄漏门）。纯机械、可用 word-diff 自证零语义的迁移
（路径 token、命令改名、底盘移植）不属此列——它们是 orch 对活文件与框架底盘的
维护职责。

### Instance A（557e66f）— design-prompt 三处死指针 token 替换

- **事实**：三份 design-prompt 各 1 行，`workflow/dispatch/coverage_hole.md`
  → `workflow/fail/coverage_hole.md`（跟随 0.7.0 canon 重排），referent 未变、
  word-diff 自证纯 token swap、零行为内容。
- **Verdict：未越实质边界。** 与 orch 对 CLAUDE.md/testplan/bugs 表头的路径
  迁移同类，是活文件维护。**但** design-prompt 是 rev 行为泄漏门的受管制品，
  故此类机械编辑须留 rev 记录——本记录即提供该 acknowledgment。**不 revert**
  （revert 会还原死指针，更糟）。
- **却有一条现行 corrective（本卡新查出）**：Instance B 的 0.8.0 重排把
  `workflow/fail/` 整个折进 `workflow/bugs.md`（"## Dispatch: coverage hole"
  节），`workflow/fail/coverage_hole.md` **已不存在**；而三份 design-prompt
  当前仍写 `workflow/fail/coverage_hole.md`（`uvm_env.md:99`/`sva_bind.md:81`/
  `functional_coverage.md:127`）——**死指针再次出现且无门禁察觉**。这属
  FB-23/25/27"无消费者/无门禁校验 workflow 路径引用"家族。**Corrective（orch
  执行，非 revert）**：把这三处再迁到 0.8.0 现址（`workflow/bugs.md` 的
  coverage-hole dispatch 节），同 Instance A 的纯 token 迁移形态；rev 不代做
  （越 rev 隔离，且我不编辑 design-prompt）。

### Instance B（19af140 + 4df41b2）— `.claude/agents/*` 底盘移植 + 新增 orch.md

- **事实**：0.8.0 删除 `fwsync.py`（`.claude/agents/` 不再自动生成、"转静态
  5 份"），orch 手工移植 arch/de/dv/rev 四卡（命令改名、项目名泛化、退休动词
  订正见 FB-27）并从上游 0.8.0 渲染新增 orch.md。gated by `make selftest
  60/60` + `make check` 绿。
- **Verdict：未越边界；准予底盘移植豁免（on record）。** `.claude/agents/`
  与 `.claude/skills/` 是框架底盘，非 §0 列举的四类技术制品；子代理正是**从
  这些文件渲染**的，移植底盘天然是 orch 职责，且 fwsync 已删、无第二条通路。
  新增 orch.md 在当时是对上游 0.8.0 的忠实渲染（正确）。

### Instance C（4efcd0d）— 删 orch.md + 并入 /dispatch + CLAUDE.md §0

- **事实**：删除 `.claude/agents/orch.md`（86 行），把其操作性内容并入
  `.claude/skills/dispatch/SKILL.md` + 改 `CLAUDE.md` §0 指针。依据 FB-28。
- **Verdict：未越边界；准予底盘修复豁免（on record）。** FB-28 的机制论证
  成立且锋利：`.claude/agents/*.md` 只在被**派发**时注入子实例系统提示，主
  会话（orch 自己）永远收不到 orch.md 正文——一份通篇"You are orch"的文件唯一
  读不到它的就是主会话。删除并把内容折进 /dispatch（派卡前载入）+ CLAUDE.md
  §0（常驻）是对真实机制缺陷的修复，属底盘维护。
  - **一条留档告诫**：CLAUDE.md §0 是隔离宪章，改它是高后果动作。本次编辑是
    忠实的机械指针重指（orch.md → /dispatch），gated by selftest，可接受；但
    今后对 §0 的任何**语义**改动（非纯指针/路径）应经 rev 过目，不得径改。

### Overall（Item 3）

三处均**未越 dispatcher-only 的实质边界**——无一产出 RTL/TB/design-prompt
内容/spec 内容；三处都是底盘或路径的机械维护，本就是 orch 职责。B、C 准予
底盘移植/修复豁免并留档；A 同样豁免，**外加一条现行 corrective**：0.8.0 后
三份 design-prompt 的 `workflow/fail/coverage_hole.md` 已成死指针，orch 须
完成迁移至 `workflow/bugs.md` 现址（纯 token，非 revert）。

**面向未来的线（可证伪）**：orch 可对活文档（含 design-prompt）做**机械可证、
零语义**的迁移（路径 token / 命令改名），前提 (a) word-diff 自证为纯 token
swap 且 referent 存在，(b) 落在一份 rev 记录里。任何改变**行为含义**的编辑
必须退回 arch + rev 门。此线的证伪点：若某次 orch 编辑的 diff 不能被 word-diff
证明为零语义 token swap，即越界。
