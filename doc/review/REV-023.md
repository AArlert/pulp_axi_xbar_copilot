## 2. 逐条结论（本卡六问 + 需裁决四问）

### Q1（taxonomy 终判）— 是否维持 SPEC_ISSUE（候选）？

**维持 SPEC_ISSUE，但须重框：不是"spec 蒸馏太松"，而是"上游内部 doc-vs-RTL 约束
松紧矛盾，spec 忠实于文档侧"，性质为潜伏（latent）、非当前活跃。**

成本阶梯逐级复核：
- **TOOL_ENV — 排除**：静态阅读缺口，与 seed/机器/build 无关。
- **TB_BUG / CONSTRAINT_BUG — 排除**：三张表 `start<end` 严格成立（§1 j-m），refmodel
  `decode_mst_port`（L354）半开区间溯 spec §3.2.1、非抄 RTL；TB 侧无错误期望值、无
  越界约束。
- **DUT_BUG — 不采纳为终判，但须记一笔上游事项**：`check_start` 比 xbar.md 文档更严
  （L148 `<` vs L26 `<=`），且 addr_decode 头注释 L26 与 L36-38 自相矛盾（§1 d/e）。
  这是一处**真实的上游 doc-vs-RTL 不一致**。但本项目 DUT 只读、不改行为，且当前无
  场景令 DUT 产出任何 spec 违例输出（无构造触及），故不落 DUT_BUG 终态；按 `CLAUDE.md`
  §6"疑似上游不一致走上游 issue"精神，**建议 orch 记一条上游 issue 线索**（xbar.md
  文档 `<=` 与 common_cells `check_start` `<` 不一致；且 addr_decode 头注释内部
  L26/L36-38 亦不一致）——非本条阻塞项。
- **SPEC_ISSUE — 命中，但须限定支别**：`workflow/bugs.md` SPEC_ISSUE 两支——(i)
  "spec.md contradicts upstream documentation" 或 (ii) "does not define the behavior
  at all; DUT and TB each defensible under a different reading"。
  **本条不命中 (i)**——spec §3.2 条 2 **不**与上游文档矛盾，恰恰**忠实**于 xbar.md L26
  (§1 a/c)。**命中 (ii) 的变体**：spec（跟随文档）判 `start==end` 合法、RTL 断言判其
  非法，构成"DUT（RTL check_start）与文档/spec 各在不同读法下都站得住"的潜在两读——
  但 **(ii) 后半"当前有分歧现场"不成立**（无场景触及，§1 定量证明），故为**潜伏型
  SPEC_ISSUE**：分歧潜在、非当前存在。

**与 BUG-0045 的类别差异（须显式厘清，任务问题 3 所指）**：BUG-0045 是"spec 对 RTL
已文档化行为**沉默**"（漏一个哨兵分支）；本条是"上游**文档与 RTL 对同一构造合法性
判断相反**，spec 站文档侧"。两者方向不同（漏 vs 矛盾），但**都是潜伏、都无当前场景
触及**。**关键**：本条 spec 侧**并无错误可改**——这一点比 BUG-0045 更强地否决了
"现在改 spec"（见 Q3）。

### Q2（是否真的无场景/配置触及）— 断言"三张表均 `start<end`、无 `start==end`"是否属实？

**属实，经 rev 独立核实，非采信转述。** 见 §1(j)(k)(l)(m) 逐表核 + tb 全域 addr_map
构造点扫描：三张表全派生自 `gen_addr_map`（`start<end` 严格），`ADDR_MAP_OV1` 改的是
`start_addr='0`（合法起址）非 `end_addr`、且改后 `start=0<end=0x1000_0000` 仍严格；
无任何运行时改表逻辑构造 `start==end`。`REGION_SIZE`/`NO_ADDR_RULES`/`ADDR_W` 固定
localparam、配置矩阵不改之 ⇒ 无配置能构造空区间 rule。**结论：pass。** 补一笔：因
`INC_ASSERT` 在本项目 sim 带电（§1 h），一旦真有人构造 `start==end`(end≠0)，第一个
见红的是 `check_start` 的 UVM 断言报告（§1 i），而非 scoreboard 期望值分歧——这印证
guard 应走"先补场景行 + 先裁决是否收紧构造约束"的顺序，不许 DV 直接跑这类表。

### Q3（处置路径三选一或更优）— 采纳 (b) ACCEPTED@M5；**独立否决 (a)**；排除 (c)

**采纳 (b) `ACCEPTED@M5`（residual risk，到期里程碑 M5，点名本 REV-023）。**

**独立否决 (a)「现在把 spec §3.2 条 2 收紧为严格 `<` + Change record + 重 pin」——
其前提被本 rev 核实为假，且该动作会主动损害 spec 的来源忠实性。** 理由三重：
1. **前提证伪（核心）**：任务问题 3 与 BUG-0046 行都预设 (a) 是"改一个文字性错误、
   成本极低"。**但 §1(a) 证明 spec 的 `<=` 不是错误——它忠实于许可来源 xbar.md L26
   "less than or equal to"**。把 spec 收紧为 `<` 不是"订正笔误"，而是**让 spec 主动
   偏离其权威文档来源、转而对齐 RTL 的更严约束**——这正是 `CLAUDE.md` §4/不变量 4
   禁止的方向（期望/约束从 pinned spec 派生、spec 从许可文档来源蒸馏，**不从被测
   RTL 抄**）。面对一处真实的上游 doc-vs-RTL 矛盾，"悄悄把 spec 改成跟 RTL 走"恰是
   本项目最忌的处置。
2. **deferred ledger（discipline rule 2）**：即便退一步认为"应记录 RTL 更严"，当前也
   无任何场景/构造需要这条更严约束（三张表已 `start<end`，无空区间生成器可约束）。
   机制/约束在 trigger fire 时落地，非"看起来该对齐"时落地。
3. spec re-pin（change record + sha 更新 + 重 pin）是重操作；为一处零当前构造、且 spec
   本就正确的潜伏矛盾付此代价不成比例。

> **注意**：任务问题 3 特意点出"本条不像 BUG-0045 那样需三者同批才可证伪、收紧
> spec 不会让任何现有场景变红"——此观察**属实**（本条确无 refmodel 死代码顾虑）。
> 但它**不足以**让 (a) 成立：否决 (a) 的理由**不是**"会造不可证伪死代码"（那是
> BUG-0045 的理由，此处不适用），**而是更前置的**——(a) 要改的东西本身没错，改了
> 反而破坏 spec 对权威文档的忠实。结构差异为真，结论仍是不做 (a)。

**排除 (c)「WONTFIX」**：`workflow/bugs.md` status 语义"WONTFIX may not mean 'later'"。
本 rev 判断此矛盾**应当在 M5 复访**（M5 = 验证方法学拓展里程碑，见近期提交
`docs(m5): …验证方法学拓展提案过 rev 门禁`；其约束随机化路线一旦触及地址表随机化，

按本项目纪律应留可见 + 走上游 issue，不宜永久埋没。

**(b) 为何最诚实**：`ACCEPTED@M<n>` = "analyzed, scheduled debt"——未到期不阻塞签核、
